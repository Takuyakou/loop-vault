# Loop Vault — Codex作業計画書

設計書(`loop-vault-spec.md`)を実装に落とすための進行管理ドキュメント。
**設計書が仕様の正、本書は「どう作業を切り、どう検収するか」の正。**

---

## 0. 前提と運用ルール

### リポジトリ準備(Codexに投げる前に人間がやること)

1. 空リポジトリ `loop-vault` を作成
2. `docs/spec.md` として設計書(loop-vault-spec.md)をコミット
3. `docs/plan.md` として本書をコミット
4. Codexの環境設定: Node 20+ / Rust stable / `cargo` と `npm` が使えること(Tauriビルドに必須)

### PR運用

- **1タスク(V-XX)= 1PR** を原則とする。V-10〜V-17のUI系は2タスク束ねてもよいが、Phase 0〜1のドメイン系は必ず単独
- PRタイトル: `V-03: VaultRepository + atomic write + generation backup` 形式
- `[dom]` タスクはVitestテストがないPRをマージ禁止
- 各PRの説明に「設計書の対応セクション(§3.x)」を必ず記載させる

### Codexへの指示の出し方

- **フェーズ単位でセッションを切る**(Phase 0を完了・レビュー→Phase 1へ)。一括で全部投げると設計判断が雑になる
- 各フェーズ開始時に「マスタープロンプト+該当フェーズのキックオフプロンプト」を渡す
- Codexが仕様の曖昧さを勝手に埋めた場合は、diffレビューで検出して設計書の該当セクションを引用して差し戻す

## 2. 全フェーズ共通の受け入れ基準(設計書§3.1より)

1. 新規ネタ登録が10秒以内で完了する
2. 起動から「今日やるネタとNext Action」が見えるまで0クリック
3. .flpのパスを登録したネタから1クリックでFL Studioが起動する
4. データファイルを手動で壊しても直前のバックアップから復旧できる

Phase 5の最終検収でこの4つを必ず通す。

## 3. Codexが逸脱しやすいポイント(先回りチェックリスト)

- [ ] SQLiteを勝手に入れていないか(MVPは単一JSON。§Part1で決定済み)
- [ ] Next Actionを配列にしていないか(**ちょうど1つ**が仕様の核)
- [ ] 保存ボタンを作っていないか(自動保存のみ)
- [ ] ネットワーク系のTauri権限・依存を入れていないか(通信ゼロ)
- [ ] 遷移ロジックがUIコンポーネント内に書かれていないか(純関数集約)
- [ ] `updatedAt`が閲覧で更新されていないか(実質的な編集のみ)
- [ ] 作らない機能(§3.3)に手を出していないか(AI提案・波形プレビュー等)
- [ ] Mac対応の検証に時間を使っていないか(Windows優先、検証スコープ外)
