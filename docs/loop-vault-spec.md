# Loop Vault — 作曲ネタ管理アプリ 設計書

## Part 0. 全体方針(プロダクトコンセプト)

**Loop Vaultは「曲ネタのデータベース」ではなく「完成率を上げる装置」である。**

作曲が完成しない原因は、ネタ不足ではなく「①どのネタを育てるか迷う ②次の一手が決まっていない ③放置に気づかない」の3つ。Loop Vaultはこの3つだけを潰す:

1. **開いた瞬間に「今日はこれ」が1つ提示される**(迷いの排除)
2. **全ネタに「次にやること」が必ず1つだけ紐づく**(次の一手の強制。2つ以上は登録できない)
3. **放置ネタが自動で浮上する**(更新が7日止まったネタをホームで警告)

進捗は Idea → Loop → Arrange → Mix → Done の一本道パイプラインで見える化し、月1曲(=月間Done 1件)をトップに常時表示する。管理機能は増やさない。**「登録が面倒だから使わなくなる」が最大の失敗モード**なので、新規登録はタイトル+ステータスだけで完了できる(他は後から)。

Chord Dripとの関係: Chord Dripは素材の入口、FL Studioは制作の現場、Loop Vaultは進行管理の司令塔。連携はMVPでは「コード進行メモ+MIDIファイルパス」で受け、将来はChord Dripの出力JSONをそのまま添付できる口を用意しておく。

## Part 1. 技術方式の比較

分岐点は1つ: **要件13・14(MIDI/音声/FLプロジェクトのパス管理)を「ただのテキスト」にするか「開けるリンク」にするか。** ブラウザはローカルパスを開けない。ここで体験が決定的に変わる。

### 案A: Web SPA(React + Vite)+ localStorage

- ✅ 最速。Chord Drip(MVP)と完全に同じスタック
- ✅ デプロイ不要、ブラウザで完結
- ❌ ファイルパスは**コピペ用テキスト止まり**。「FLプロジェクトをすぐ開く」体験が作れない
- ❌ localStorageは約5MB・ブラウザのデータ消去で全損リスク。曲ネタ資産の保管庫として不安
- ❌ 将来のMIDI添付・音声プレビュー・バックアップがすべて壁に当たる

### 案B: Web SPA + IndexedDB + File System Access API

- ✅ IndexedDBで容量問題は緩和、ファイルハンドル保持も一応可能
- ❌ File System Access APIはChromium限定+許可UIが頻出しUXが悪い。エクスプローラで開く/FLで開くは結局不可
- ❌ 「ブラウザアプリの限界」を工夫で埋める工数が、デスクトップ化する工数を上回る

### 案C: Tauri v2 + React + TS + ローカルJSONストア(→推奨)

デスクトップアプリ。データは単一JSONファイル(アトミック書込+世代バックアップ)、Repositoryパターンで将来SQLiteに差替え可能。

- ✅ **「FLプロジェクトを開く」「エクスプローラで表示」がOSシェル経由で実現**(このアプリの核体験)
- ✅ フロントはReact+TS+Viteそのまま=Chord Dripと知見・コンポーネント・型を共有できる
- ✅ データが実ファイル(`loopvault/data.json`)なので、バックアップ=ファイルコピーで成立。ユーザーが自分の資産を自分で握れる
- ✅ 数十〜数百件規模ならフィルタ・検索は全件メモリ処理で十分(SQLite不要)。実装が最小
- ✅ Chord Dripの将来Tauri化と技術基盤が揃う(学習コストの二重投資を回避)
- ⚠️ Rustツールチェーンの初期セットアップが必要(ただしMVPでRustを書くのはシェルopen等の数十行程度。Tauri v2はプラグインで大半カバー)
- ⚠️ 配布はローカルビルドでOK(自分用途)。署名等は不要

### 案D: Electron + React + SQLite

- ✅ 実績豊富、Node APIで何でもできる
- ❌ バイナリ150MB級・メモリ食い。個人ツールに対して重装備
- ❌ SQLiteはこの規模(数百件・単一ユーザー・リレーション浅い)に対して、マイグレーション管理コストが先に立つ
- ❌ 将来Chord DripをTauri化する計画と基盤が割れる

### 保存方式の比較(案C内での選定)

| | 単一JSONファイル | SQLite | Markdownファイル群(Obsidian風) |
|--|--|--|--|
| 実装速度 | ◎ | △(スキーマ・マイグレーション) | ○ |
| クエリ/絞込 | ○(全件メモリで十分) | ◎ | △ |
| バックアップ | ◎(ファイルコピー) | ○ | ◎ |
| 破損耐性 | ○(アトミック書込+世代で担保) | ◎ | ○ |
| 将来のバージョン管理・週次レビュー | △→SQLite移行 | ◎ | △ |
| ユーザーが直接読める | ◎ | ✕ | ◎ |

→ **MVPは単一JSONファイル**。`VaultRepository` インターフェースを切っておき、レコードが数千件・バージョン履歴・週次レビュー集計が現実になった時点でSQLite実装に差替える。

### 比較まとめ

| | 核体験(ファイルを開く) | 実装速度 | データ資産の安全性 | Chord Drip親和性 |
|--|--|--|--|--|
| A Web+localStorage | ✕ | ◎ | ✕ | ○ |
| B Web+FS Access | △ | △ | △ | ○ |
| **C Tauri+JSON** | **◎** | **○** | **◎** | **◎** |
| D Electron+SQLite | ◎ | △ | ○ | △ |

## Part 2. 推奨構成: 案C(Tauri v2 + React + TS + JSONストア)

### 採用理由

1. **「FLプロジェクトを1クリックで開く」は完成率に直結する体験**であり、これを捨てた時点でLoop Vaultは「きれいなメモ帳」に格下げされる。デスクトップ化は贅沢ではなく要件。
2. 1〜2週間の制約に対し、Tauriの追加コストは初日のセットアップ+シェルopen実装のみ。**UI・状態管理・データ処理は全部いつものReact+TS**で書ける。
3. データを単一JSONファイルにすることで、**バックアップ設計(§3.10)がほぼ無料で手に入る**。曲ネタは数年育てる資産なので、DBの中に閉じ込めないことに価値がある。
4. Chord Drip(将来Tauri化予定)と基盤・スキーマ思想(Zod検証、Repository抽象化、宣言的JSON)を完全共有でき、2アプリの連携が「JSONの受け渡し」に単純化される。

### スタック確定

- Tauri v2(plugin: fs, dialog, opener/shell)
- React 18 + TypeScript + Vite
- 状態管理: Zustand(小規模・非同期Repositoryと相性良)
- 検証: Zod(データファイルのロード時検証・Chord Drip連携JSONの検証を共通化)
- テスト: Vitest(ドメインロジック=遷移・進捗計算・フォーカス選定は純関数化)
- スタイル: Tailwind(手早く。凝らない)

## Part 3. 設計詳細

### 3.1 MVP要件定義

| ID | 機能 | 備考 |
|----|------|------|
| L-01 | 曲ネタCRUD | 新規登録は**タイトルのみ必須**(即登録→あとで肉付け) |
| L-02 | メタ管理 | BPM / Key / Genre / Mood(複数可) / 参考曲(複数: タイトル+URL+メモ) / コード進行メモ / 作成日・更新日(自動) |
| L-03 | アセット管理 | MIDI・音声・FLプロジェクト等のパス+メモ(複数)。**「開く」「フォルダで表示」ボタン付き** |
| L-04 | ステータス管理 | Idea / Loop / Arrange / Mix / Done / Hold / Abandoned(遷移ルールは§3.6) |
| L-05 | Next Action | 各ネタに「次にやること」を**ちょうど1つ**。完了→次を入力のサイクル |
| L-06 | 一覧+絞込 | ステータス・Genre・Mood・テキスト検索。並び: 更新日/作成日/BPM |
| L-07 | ホーム(Focus) | 今日育てるネタ1件の提示+月間進捗+放置警告(§3.8) |
| L-08 | 月間進捗 | 今月のDone数/目標1、パイプライン内訳、過去月の実績 |
| L-09 | データ保全 | アトミック保存、世代バックアップ、手動エクスポート/インポート |

受け入れ基準: 「新規ネタ登録が10秒以内で完了する」「アプリ起動から『今日やるネタとNext Action』が見えるまで0クリック」「.flpのパスを登録したネタから1クリックでFL Studioが起動する」「データファイルを手動で壊しても、直前のバックアップから復旧できる」

### 3.2 非機能要件

- 起動〜表示可能まで2秒以内(数百件想定)
- 全操作ローカル完結・ネットワーク通信ゼロ(テレメトリなし)
- 保存は操作ごとに自動(保存ボタンなし)。書込はデバウンス500ms+アプリ終了時フラッシュ
- ドメインロジック(遷移・フォーカス選定・進捗計算)は純関数でVitestテスト必須
- Windows優先(FL Studio前提)。Mac対応はTauriなのでほぼ無料だが検証はスコープ外

### 3.3 作らない機能(MVP)

音声解析 / AI分析・AI提案 / クラウド同期 / 複数ユーザー / DAW直接連携(プラグイン等) / 自動コード・BPM解析 / 高度な統計 / SNS投稿 / サブスク / 音声波形プレビュー / バージョン管理 / 週次レビュー / タグの自由増殖(GenreとMoodは定義済みリスト+追加可、程度に留める)

### 3.5 データモデル

```typescript
type Status = "idea" | "loop" | "arrange" | "mix" | "done" | "hold" | "abandoned";
type AssetType = "midi" | "audio" | "flp" | "other";

interface SongIdea {
  id: string;                 // uuid
  title: string;              // 必須・1〜80字
  bpm?: number;               // 40〜300
  key?: string;               // "F", "Am" 等の自由入力(候補サジェストあり)
  genre?: string;
  moods: string[];
  status: Status;
  prevStatus?: Status;        // Hold/Abandonedからの復帰先
  nextAction: {
    text: string;             // 空文字=未設定(未設定はUIで強く警告)
    updatedAt: string;        // ISO8601
  };
  chordMemo: string;          // コード進行のテキストメモ
  references: { title: string; url?: string; memo?: string }[];
  assets: {
    id: string;
    type: AssetType;
    path?: string;            // 絶対パス(任意=メモだけでも可)
    memo?: string;
    missing?: boolean;        // 起動時/開く時にパス消失を検知したら立てる
  }[];
  chordDrip?: unknown;        // 将来: Chord Drip出力JSONの格納口(MVPでは未使用・保持のみ)
  statusHistory: { status: Status; at: string }[];
  createdAt: string;
  updatedAt: string;          // 実質的な編集で更新(閲覧では更新しない)
  completedAt?: string;       // Done到達時刻(月間集計に使用)
}

interface VaultFile {
  app: "loopvault";
  fileVersion: 1;             // マイグレーション用
  settings: { monthlyGoal: number };  // 既定1
  ideas: SongIdea[];
}
```

### 3.6 ステータス遷移設計

```
Idea → Loop → Arrange → Mix → Done      (前進は1段ずつ。後退も1段ずつ可)
  │      │       │        │
  └──────┴───────┴────────┴──▶ Hold / Abandoned(どこからでも)
Hold → prevStatusへ復帰
Abandoned → prevStatusへ復帰可(ボツ撤回を許す。削除とは別物)
Done → Mixへ戻し可(リマスター等)。completedAtは初回Done時刻を保持
```

ルール:
- 遷移は関数 `transition(idea, to): Result` に集約し、不正遷移(Idea→Mix等の飛び級)はエラー。**飛び級を禁止するのは「Arrangeを飛ばした未完成癖」を仕組みで防ぐため**
- 前進遷移時、Next Actionが完了済み(空)ならそのまま、残っていれば「持ち越すか書き換えるか」をダイアログで確認
- Hold遷移時は理由メモを促す(任意)。Abandoned遷移時は確認ダイアログ
- 全遷移をstatusHistoryに記録(進捗表示・振り返りの原資)

### 3.7 Next Action設計(最重要機能)

- 常にちょうど1スロット。追加ではなく**上書き**のUI(「次にやることリスト」に絶対にしない)
- 「✓ 完了」を押すと: テキストをクリア→**即座に次のNext Action入力を要求**(空のまま閉じることも可能だが、Home/一覧カードに ⚠未設定 が出続ける)
- 完了時にupdatedAtが更新される=「触った」ことになる=放置警告が解除される
- 入力プレースホルダに例文をローテーション表示(「ベースを差し替える」「Bメロのコードを試す」等)して、粒度の手本を示す

### 3.8 Focus(今日はこれ)選定ロジック

対象: status ∈ {idea, loop, arrange, mix}(Hold/Abandoned/Doneは除外)

優先度スコア(降順で1件目をFocusに):
1. status重み: mix 4 > arrange 3 > loop 2 > idea 1(**完成に近いものを先に押し切る**=月1曲最短路)
2. 同点なら放置日数(updatedAtからの経過)が長い順
3. Next Action未設定のネタは、スコアに関わらず「⚠先に次の一手を決める」枠として別掲

放置警告: updatedAtから7日超のネタをHomeに列挙(タップで詳細へ)。14日超は「Holdにしますか?」を提案(**放置とHoldを区別させ、罪悪感の在庫を減らす**)。

### 3.9 月1曲進捗の設計

- 今月のDone数(completedAtが当月)/ monthlyGoal をバー表示+残日数
- パイプライン内訳(各ステータス件数)を横並び表示 — 「Mixに1件いる=今月いける」が読める
- 過去12ヶ月のDone数をミニ棒グラフ(statusHistoryから算出。高度な統計はやらない)
- Done到達時はちょっとした祝福演出(1秒のコンフェッティ程度)。**完成の快感を強化学習させる**

### 3.10 保存・バックアップ設計

- 保存先: Tauri appDataDir配下 `loopvault/data.json`(設定画面で場所を表示・エクスプローラで開ける)
- **アトミック書込**: `data.json.tmp` に書いて成功後リネーム(書込中クラッシュで全損させない)
- **世代バックアップ**: 起動時に1回 `backups/data-YYYYMMDD-HHmm.json` を作成、最新20世代を保持(それ以前は自動削除)。日常利用でおよそ20日分
- 手動エクスポート: 任意の場所へ `loopvault-export-{date}.json` 保存(ダイアログ)。インポートは全置換/マージを選択(マージはid衝突時に新しいupdatedAt優先)
- 復旧UI: データ破損検知時、バックアップ一覧から選んで復元できる画面を出す

### 3.11 エラーハンドリング設計(異常系カタログ)

| ケース | 検知 | 挙動 |
|--------|------|------|
| data.jsonが存在しない(初回) | 起動時 | 空Vaultを新規作成(エラーにしない) |
| data.jsonがJSON破損 | 起動時parse | 破損ファイルを `data.corrupt-{date}.json` に退避→最新バックアップの復元を提案。**無言で空で上書きは絶対にしない** |
| 個別レコードがスキーマ不正 | 起動時Zod検証 | 不正レコードのみ隔離(`quarantine`配列に退避)+警告表示。他レコードは正常起動 |
| fileVersionが新しい | 起動時 | 「新しいバージョンのデータです。アプリを更新してください」で読取専用起動 |
| アセットのパスが存在しない | 詳細表示時/開く時 | `missing`フラグ+赤表示+[パスを再設定]ボタン。開く操作はエラートースト |
| 「開く」対象が未対応拡張子 | 開く時 | ホワイトリスト(.flp .mid .wav .mp3 .flac .zip等)外は「フォルダで表示」のみ許可(§3.13) |
| 書込失敗(ディスクフル/権限) | 保存時 | トースト+リトライ。未保存変更がある間はウィンドウ閉時に警告 |
| インポートJSONが不正 | インポート時 | Zod検証+パス付きエラー表示(Chord Dripで設計した ImportIssue 形式を流用) |
| 削除の誤操作 | 削除時 | 確認ダイアログ+直後5秒のUndoトースト(実削除は遅延実行) |

### 3.12 Chord Drip連携を見越した設計

- MVPでの受け口: ①chordMemoにテキスト進行を貼る ②Chord Dripが出した.midをassets(type: midi)に登録 — **今日から運用可能**
- 将来の受け口: `chordDrip` フィールドにChord Dripの生成結果JSON(`kind: "chorddrip.progression"` を定義予定)をそのまま格納。読み込みはChord Drip側で設計済みの「kind識別+Zod検証+ImportIssue報告」パイプラインを共通ライブラリ化して共有
- 連携手段の想定順: 手動JSON貼付/ファイル添付 → クリップボード経由 → (Tauri同士なら)カスタムURLスキームやローカルファイル監視。**MVPでは口(フィールドとkind規約)だけ確保し、実装しない**

### 3.13 セキュリティ・ローカルデータ保護

- 通信ゼロ(Tauriのネットワーク権限を付与しない)。データは全てユーザーのPC内
- Tauri fsスコープをappDataDir配下+ユーザー指定のエクスポート先に限定
- 「開く」はOSシェル経由(opener plugin)だが、**拡張子ホワイトリスト+登録時にユーザー自身が入力したパスのみ**。実行ファイル(.exe .bat等)は登録できてもopen不可(フォルダ表示のみ)
- data.jsonには曲名・パス等の個人情報が平文で入る旨をREADMEに明記(暗号化はしない=ユーザー自身が読める価値を優先)
- インポートJSONも検証を通すまで信用しない(Chord Dripと同じ思想)

## Part 6. ポートフォリオとしてのアピールポイント

1. **課題定義の明確さ**: 「作曲が完成しない」という自分の実課題を、Focus/単一Next Action/放置検知という仕様に翻訳した — 機能列挙ではなく行動設計から入ったプロダクト思考
2. **技術選定の説明可能性**: Web/Tauri/Electron×保存方式を比較し、「ファイルを開く体験が核」という基準で選定した意思決定ログ(本書)が残っている
3. **データ資産への誠実さ**: アトミック書込・世代バックアップ・破損時の退避と復元・レコード単位の隔離 — 個人ツールでも全損させない設計
4. **拡張前提のアーキテクチャ**: Repository抽象化(JSON→SQLite)、kind付きJSONによるアプリ間連携規約 — Chord Dripとのエコシステム構想
5. **ドメインロジックの純関数化とテスト**: 遷移・スコアリング・月間集計がUIから独立してテストされている
6. **2アプリで一貫した設計言語**: Zod検証+ImportIssue+宣言的JSONという共通パターンを横展開している
