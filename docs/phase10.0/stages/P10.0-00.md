## 3. 監査B：再生の選び方と保存先

`docs/phase10.0/audit/P10.0-00-voicing-audit.md` に書く。仕様書10.3の2つの監査。

1. **`practiceVoicingOverride` を読む所の表。** カードの試聴、取り込みの試聴、曲全体の再生、進行ページ、Voicing Loop、移調練習、MIDI の書き出し、テキストの取り込み、ほかに見つかった所。各行に「ファイル:行」「何に使うか」「練習専用の意味か、人が選んだボイシング全般の意味か」を書く。
2. **コード名と合わない時の切り替え。** `resolveVoicingForUse`・`voicingCompatibility`・`attachSourceVoicing`・`canChooseSource` など、コード名との合否で鳴る音や SOURCE の選択が変わる所を全部挙げる。人が音を足したり高さを直したりして名前と合わなくなった時、どの画面で何が鳴るかを表にする。
3. **今の動きを確かめるテスト**を足す（テストだけの commit）：`src/domain/voicing/p10VoicingAudit.test.ts`。
   - (a) `playbackChoice: "CUSTOM"` で、音がコード名と合わない時に生成の音になる。
   - (b) `playbackChoice: "SOURCE"` で、音がコード名と合わない時に生成の音になる。
   - (c) `playbackChoice` が無く、`practiceVoicingOverride` が名前と合う時は、それが `sourceVoicing` より優先される。
   - テスト名の頭に「P10.0-00 current behavior」を付ける。今の動きと違えば、テストを今の動きに合わせ、違いを報告に書く（製品コードは直さない）。P10.0-01 を行う時に期待値を変える。
4. **おすすめ**を書く：直した音の保存先（`practiceVoicingOverride` でよいか、別の場所が要るか）と、P10.0-01 の最小の直し方（どの関数の、どの条件を、どのフラグで変えるか、影響する画面、必要なテスト）。**実装はしない。**

## 4. 監査C：作業データ（CorrectionModel）の実現性

`docs/phase10.0/audit/P10.0-00-correction-model.md` に書く。仕様書8章の前提の確認。

1. 取り込みの結果の時点で使えるデータ：`fullTimeline` の各項目（名前・別候補の Top-K・`sourceVoicing`）、元の音（`MidiSongData` の音と Voice）、解析前の Voice の役割、`sections`、テンポと拍子。どこから取れて、足りないものは何か。
2. **「使っている音」の対応付けの確認。** カードの `sourceVoicing.midiNotes` の高さを、その区間の元の音から探して対応が取れるかを、合成の MIDI（Git に入っている fixture）で数える。
   - 小さなスクリプトを `scripts/p10/correction-model-audit.ts` に作り、`npx vite-node` で動かしてよい（製品には入らない）。
   - 集計（カード数、対応が取れた高さ・取れなかった高さの数、`aggregated-note-set` の数など）だけを `docs/phase10.0/evidence/P10.0-00-correction-model.json` に残す。
3. **名前の候補（仕様書8.4）を出せる関数。** 任意の音の集まりから、名前の候補を複数（Top-K）返せる既存の関数があるか（解析の候補の順位付け、Live MIDI の判定、テキストのコードの解釈など）。**解析ロジックを変えずに呼ぶだけで**使えるか。使えない場合は、後の段階で困る点として報告に書く（止まらない）。
4. **名前から構成音を出せる関数**（仕様書6.4の「構成音との違い」用）。既存のものがあるか。

## 5. 基準の計測

1. **自動の計測**（合成データだけ）。結果の集計を `docs/phase10.0/evidence/P10.0-00-baseline.json` に残す。
   - 合成 fixture での、カード数と期待するカード数の差（期待値が分かる fixture だけ）。
   - 仕様書6.3の3つの要確認の規則（メロディの混ざり、打楽器の混ざり、同じ音の分かれ）を今の解析結果に当てた時に、何枚のカードに印が付くか。規則の数字を変えた時の変化。
   - 取り込みにかかる時間（既存の性能テストや合成の長い曲があれば）。
2. **要確認の判定の数字の案**を `docs/phase10.0/contracts/P10-review-thresholds.json` に置く（打楽器の「短い」の長さ、繰り返しの回数 N、メロディの混ざりの判定に使う条件など）。理由を報告に書く。合成データだけで決める。
3. **人間用の計測シート**を `docs/phase10.0/reports/P10.0-00-human-baseline-sheet.md` に作る。人間が今の画面で数曲を取り込み、取り込みから保存までの時間と、直した回数（分割・結合・名前の変更・境目・音の変更）を書き込むための表。Claude Code は表の形と書き方だけを用意し、値は書かない。
