## Snapshot, harmony, and signatures

- The immutable all-note snapshot uses canonical reduced rational timing, strict known keys, and no raw MIDI/path/name/device/Voice id/private metadata.
- `snapshotSignature` is separate from `capturedHarmony.signature`. Captured harmony requires `schemaVersion: 1` and required nullable `bassPitchClass`; its signature is lowercase SHA-256 of canonical UTF-8 JSON for exactly schemaVersion plus ordered spans, excluding signature.
- Canonical note order includes continuation booleans. Canonical harmony order includes exact span timing, root, nullable slash bass, and sorted unique allowed pitch classes.
- Captured harmony authority is repository `chordPitchClasses(symbol)` plus explicit slash bass. Gaps are honest; conflicting overlaps invalidate derived levels/context; exact duplicate overlaps canonicalize; `[start,end)` resolves boundary ties.
- Current edited harmony is comparison-only (`match`/`mismatch`/`unavailable`) and never replaces capture-time context.

## Bounds and failure semantics

- Per snapshot: at most 8,192 notes and 1,048,576 canonical UTF-8 bytes.
- Whole Vault: at most 16,777,216 serialized UTF-8 bytes at local save, export, import, migration, and merge preflight. Existing P1 coverage is import-only, so other boundaries are Stage02 work.
- 8,192 is 3.2768% of the 250,000-note intake cap (about 1/30.52); 1 MiB is 1/16 of the whole-Vault cap.
- No private corpus supports an empirical distribution claim. Evidence is synthetic/security-derived only.
- Any limit/validation failure occurs before write and preserves prior data. Only opt-in ON/requested snapshot failure uses a second snapshot-free confirmation; opt-in OFF saves normally. A valid legacy v1 Vault already above 16 MiB enters size-recovery readonly mode: add/duplicate/import/merge/export are blocked, and only a delete/shrink producing one complete <=16 MiB canonical v2 document may commit.
