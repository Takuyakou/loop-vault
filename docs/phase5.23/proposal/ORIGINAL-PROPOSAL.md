# Loop Vault 提案書 Phase 5.23 — Timeline Candidate Legibility

対象: MIDI解析後の「全曲」タイムラインにおける候補表示と採集範囲の初期値。
**本書は提案であり作業指示書ではない。** 実装時は `PLAN.md` + `stages/*.md` へ分割すること。

---

## 1. 結論

**候補の「重なり」と「偏り」を、表示と選定の両面から解消する。**

実測(145小節・候補12件)では次が同時に起きている。

- **37小節付近に5件(7 / 6 / 10 / 1 / 9)が縦に重なる** — 同じ区間を長さ違いで5回切り出している
- 中央に3件、その隣に3件が固まる
- **40〜90小節、100〜140小節がほぼ空白** — 曲の半分以上に候補が存在しない

「候補が12件ある」のではなく、**実質3〜4箇所を12回切り出している**。これが「使いやすくなっていない」の実体である。

## 2. 診断

### 2.1 重なりの原因

候補は「開始小節を1ずつずらした全 4/8/16 小節窓」から生成され、スコア上位が選ばれる。良い区間は**その 4小節版・8小節版・16小節版がすべて高スコア**になるため、上位を占有する。

Phase 4.1 で診断した構造がそのままUIに露出している。

### 2.2 空白の原因

40〜90小節に候補が無いのは、そこに和音が無いからではない。**左端の区間がスコア競争で勝ち続けた結果**である。

Phase 4.1 で提案した「セクション被覆ファースト」は**未実装のまま**であり、本スクリーンショットはその問題が視覚化された状態である。

### 2.3 これは既知パターンの再発

P5.18.2 で「1つのVault進行が複数の行に見える」section-row 重複を修正した。**同じ問題が、別の画面で起きている。**

あのときの解決は `{ideaId, blockId}` によるグループ化だった。ここでは**区間の重なりによるグループ化**が対応する。

## 3. 改善案

### 3.1 A — 重なり候補のグループ化(最優先・表示層のみ)

区間が大きく重なる候補を**1本のバーに束ね、長さを切り替えられる**ようにする。

```
現在                          改善後
[======= 7 =======]           [======= 主候補 =======] ▾ 4 / 8 / 16小節
[===== 6 =====]
[= 10 =]
[= 1 =]
[= 9 =]
```

- グループ化の基準は **IoU(区間の重なり率)** が閾値以上
- **代表は決定的に選ぶ**: 最長 → 最高スコア → 開始小節の早い順 → 安定ID順
- グループ内の他候補は**捨てず、長さ切替として提示**する
- **候補生成・スコアリングには一切触れない**(表示層のみ)

これにより、12件の候補が実質3〜4本のバーとして見え、**曲のどこに何があるかが一目で分かる**。

### 3.2 B — 和声密度の背景表示(軽量)

帯の背景が現在は無地であり、**候補が無い場所に何があるのか分からない**。

- 小節ごとの**和声イベント密度**を薄いヒートマップとして敷く
- 「候補は無いが和音は動いている」区間が見える
- **手動ドラッグの手がかり**になる(現在は暗闇に向かってドラッグしている)

既存の Full Timeline データから導出でき、新しい解析を必要としない。

### 3.3 C — 候補の被覆保証(本質的・選定ロジック)

候補数を増やすのではなく、**配分を変える**。

- 曲をセクション(編成変化・和声の新規性)に分割する
- **各セクションから最低1件を選ぶ**
- 残り枠を従来のスコア順で埋める
- 受け入れ指標: **和声活動のある小節のうち、いずれかの候補に覆われる割合 ≥ 90%**

これは Phase 4.1 の未実装分の回収である。**A/B と違って候補選定ロジックに入るため、リスクと工数が一段上がる。**

## 4. 採集範囲の初期値

現在の初期値は **「37.1〜37.4 / 1小節 / 1イベント」= コード1個**である。採集の出発点としては狭すぎる。

| 項目 | 現在 | 提案 |
|---|---|---|
| 初期選択 | コード1個 | **最上位候補(最長・最高スコア)の全体** |
| スナップ既定 | 拍 | **小節**(Contract 06 適合セクションを作りやすい) |

**スナップ切替(小節 / コード境界 / 拍)は維持する。** 既定値だけを変える。

## 5. 実装順序と理由

| 順 | 案 | 触る層 | リスク |
|---|---|---|---|
| 1 | **A** グループ化 | 表示のみ | 低。候補生成に触らない |
| 2 | **初期値**(§4) | UI設定 | 低 |
| 3 | **B** 密度背景 | 表示のみ | 低 |
| 4 | **C** 被覆保証 | 候補選定 | 中。回帰確認が必要 |

**A だけで体感は大きく変わる。** C は本質的だが重いため、A/B の効果を見てから判断してよい。

## 7. Gate

- **A/B は候補生成・スコアリング・Contract 06 に一切変更を加えないこと**(表示層のみであることをdiffで確認)
- グループ化の代表選出が決定的(同一入力 → 同一表示)
- グループ内の候補が**失われていない**こと(長さ切替から全て到達できる)
- C を実施する場合: 被覆率 ≥ 90%、既存コーパスで退行なし、Chapter 3 Seed は −0.25pp 以内
- キーボード操作(←/→ 移動、Shift+←/→ 伸縮、G スナップ、Space 試聴、Enter 編集)が維持されること
- 320px / 実効200% / reduced motion / Axe serious-critical
- `fileVersion = 1` / Vault schema / `defaultAnalyzerMode` 不変
- 既存テスト全通過

## 8. やらないこと

- 候補数の上限変更(**配分の問題であり数の問題ではない**)
- Contract 06 の緩和
- 解析エンジン・スコアリング・境界検出の変更(A/B の範囲では)
- タイムラインへの波形表示・オーディオ解析
- 既存のスナップ切替・キーボード操作の削除

## 9. 位置づけ

Phase 4.2 で「範囲を手で編集できる」ようにした。しかし**どこを編集すべきかが見えない**ままだった。

本フェーズは、その手前の「**曲のどこに何があるか**」を読めるようにする。候補は増やさない。**同じ候補を、正しく見せる。**
