# Loop Vault 提案書 Phase 5.26 — Local Harmonic Rhythm / Spelling / Altered Tensions

対象: 演奏MIDI(ボサノバ 2-feel)で観測された3系統の誤り。
**本書は提案であり作業指示書ではない。** 実装時は `PLAN.md` + `stages/*.md` へ分割すること。

---

## 1. 結論

**実データで観測された誤りを、性質ごとに3つに分けて扱う。**

| Track | 内容 | 実害 | 規模 |
|---|---|---|---|
| **A** | 和声リズムの **Local 推定**(P5.24 の fallback を解消) | **最大。誤り3件すべての原因** | 中 |
| **B** | 異名同音の綴りをキーに従わせる | 小(和声内容は正しい) | **小** |
| **C** | b9 / b13 の候補生成と順位 | 中 | 中 |

**Track A が本命である。** B は安く、C は実データによる裏付けが初めて得られた項目である。

## 2. 観測データ

期待進行(E major / 122 BPM / 4/4 / 8小節):

```
| E6/9 | G#7(b13) | C#m9 → Cmaj7 | Bm9 → E13 |
| Amaj9 | Am6 | E/G# → C#7(b9) | F#m9 → Amaj7/B |
```

現在の解析結果:

| 小節 | 期待 | 現在 | 分類 |
|---|---|---|---|
| 1 | E6/9 | E6/9 | 一致 |
| **2** | **G#7(b13)** | **Ab7 → F#13** | **A + B + C** |
| 3 | C#m9 → Cmaj7 | 一致 | — |
| 4 | Bm9 → E13 | 一致 | — |
| **5** | **Amaj9** | **Amaj9 → Amaj9/Ab** | **A** |
| **6** | **Am6** | **Am6 → F#m7b5** | **A** |
| 7 | E/G# → C#7(b9) | E/Ab → C#7 | B + C |
| 8 | F#m9 → Amaj7/B | F#m9 → Amaj9/B | B(表記揺れ) |

**MIDIの破損・テンポ・Voice分離はいずれも正常。** 誤りは解釈側にある。

### 2.1 P5.24 が発火していなかった

診断によれば、このファイルでは:

```
harmonicRhythm      = mixed-global-periodicity
統合結果             = unsupported-harmonic-identity
→ 安全側の従来解析へ fallback
```

**P5.24 が最も効くはずのケースで、一度も発火していない。**

公式コーパスで5指標が baseline と完全一致したのも、同じ理由(発火ゼロ)である可能性が高い。P5.24 は「安全に不活性」であったが、**問題を解いてはいない。**

## 3. Track A — 和声リズムの Local 推定

### 3.1 fallback 原因① `mixed-global-periodicity`

この曲は**1小節1コードと1小節2コードが混在**している。

```
1小節1コード: 1, 5, 6
1小節2コード: 2, 3, 4, 7, 8
```

**Global 一定の推定は原理的に成立しない。**

P5.24 提案書 §11 懸念③で「Global で足りるか未検証。サビだけ和声リズムが倍になる曲は普通にある」と記した。実際には**曲の途中で小節ごとに混在する**形で、予想より早く現れた。

### 3.2 対処: 推定の単位を小節へ下げる

- 和声リズムを **Global 一定ではなく、小節(またはセクション)ごとに推定**する
- 各小節で「1コード / 2コード」を、その小節内の証拠から決める
- **証拠は P5.24 §4.2 のものを流用**(ベース変化周期・セル内一貫性・セル間分離度・強拍整列)
- 曲全体で単一周期が強く出る場合は、従来どおり Global を使う(**Global を捨てるのではなく、Local を追加する**)
- 小節単位でも confidence が低ければ `unknown` → legacy fallback(**この規律は維持**)

### 3.3 fallback 原因② `unsupported-harmonic-identity`

Am6 / F#m7b5 のような同一構成音ペア、および b9/b13 を含む和音で、統合器が identity を確定できずに降りている。

- **統合の判定に identity 確定を必須にしない。** 統合は「同一の和声状態か」を判定するものであり、その状態に**どの名前を付けるかは後段の仕事**である
- identity が確定しない場合でも、PC集合・ベース・支持音の一致で統合可否を判断できる
- 名前付けは統合後に行う(Track C がここに効く)

### 3.4 これで直るはずの誤り

| 小節 | 誤り | 原因 |
|---|---|---|
| 2 | `Ab7 → F#13` | 後半で Bass が F# へ動く |
| 5 | `Amaj9 → Amaj9/Ab` | 後半で Bass が G# へ動く |
| 6 | `Am6 → F#m7b5` | 後半で Bass が F# へ動く |

**3件すべてが同じ原因である: 2拍単位の判定で、後半のベース経過音を新しいコードと解釈している。**

ボサノバの 2-feel は、1つの和音の中でベースが動く演奏形式そのものであり、**このジャンルでは構造的に発生する**。

### 3.5 ベース経過音の扱い

Local 推定で「この小節は1コード」と判定されたなら、**小節内のベース移動はコードチェンジではなく経過音**として扱う。

- ベースレーンの動きが**その小節の和声状態の内部**にあるなら、slash bass の候補にはするが**新しいコードルートにはしない**
- 経過音として扱った事実を診断に残す

## 4. Track B — 異名同音の綴り

### 4.1 症状

| 現在 | 期待 |
|---|---|
| `Ab7` | `G#7` |
| `E/Ab` | `E/G#` |

**和声内容は完全に一致している。** 綴りだけの問題である。

### 4.2 対処

**既存のキー推定結果を、綴りの決定に使う。**

- キーが E major(♯4個)なら、**♭系の綴りを選ばない**
- 調号に含まれる音は調号どおりに綴る(G#, C#, D#, F#, A#)
- 借用和音・セカンダリードミナントも、**キーの調号を基準に綴る**
- キーが `unknown` の場合は現行の挙動を維持する

**これは表示層に近い変更であり、判定・スコアリングに影響しない。** 3つの Track の中で最も安全かつ安価である。

### 4.3 `Amaj9/B` vs `Amaj7/B`

B が A の 9th でもあるため生じる表記揺れ。**構成音は同一。**

規約として、**ベース音がコードの構成音として説明可能な場合、上部構造の名前にそれを含めない**ことを検討する(`Amaj7/B` を選ぶ)。ただし優先度は低く、**Track B の必須項目とはしない。**

## 5. Track C — b9 / b13

### 5.1 症状

| 期待 | 現在 | 状態 |
|---|---|---|
| `G#7(b13)` | `Ab7` | **b13 が候補生成されていない** |
| `C#7(b9)` | `C#7` | **候補の3番手にはいたが、順位で負けた** |

**この2つは別の問題である。**

- b13: **生成の問題**
- b9: **順位の問題**(生成はできている)

### 5.2 これが実データによる裏付けである

Phase 4.6 で「未生成コードの59%が A7b9」と判明したが、そのコーパスは **8家族 × 40件の均等合成**であり、A7b9 の比率はコーパス設計の産物だった。そのため「実使用でも問題か」が判断できず、**identity バグ解決まで保留**としていた。

**今回、実際に採集したい曲で b9 / b13 が現れた。** しかも b9 は候補に入っていて順位で負けている。**合成コーパスからは得られなかった優先度の証拠**である。

### 5.3 対処

**b13(生成)**
- ドミナント7thに対する b13 を候補として生成する
- **既存テンプレートを増やさず、コア(dom7)+ テンションの組合せとして列挙する**(Phase 4.6 で議論した合成方式。テンプレート数を増やすと部分一致バイアスが悪化する)

**b9(順位)**
- 候補には入っているため、**スコアリング側の問題**
- ただし**スコアを直接いじらない**。まず「なぜ単純な C#7 が勝つか」を診断で確認する
- b9 が実際に鳴っている(持続的・強拍)場合に、それが証拠として十分に効いているかを測る

### 5.4 慎重に進める理由

Phase 4.4〜4.5 の教訓により、**スコアリングの変更は退行を招きやすい**。

- Track C は **shadow から始める**
- **rank 1 を変える変更は、既存コーパスの回帰確認を必須とする**
- b9/b13 を追加した結果、**単純なドミナントが誤って b9/b13 になる**ことが最大のリスク。否定テストを必ず用意する

## 7. Gate

### 共通
- 本ファイルの期待進行に対する一致数が改善すること(現在 5/8 小節が完全一致)
- 既存コーパスで退行なし(Chapter 3 Seed は −0.25pp 以内)

- **P5.24 の Hard Negative A-K が全て維持されること**(False Merge Rate 0 / Over-segmentation 0)

- **Local 推定を追加しても、Global で足りる曲の結果が変わらないこと**

### Track B 固有
- キー E major で `Ab` 表記が出ないこと
- **和声内容(PC集合)が一切変わらないこと**(綴りのみの変更であることの証明)

### Track C 固有
- **単純なドミナントが誤って b9/b13 になっていないこと**(否定テスト)

## 8. 懸念

### 懸念① Track A は P5.24 の設計変更である

P5.24 は Global 一定を前提に組まれている。Local へ拡張することは、**その前提を変える**。

- **Global を捨てず、Local を追加する**形にすること(§3.2)
- P5.24 の A-K が全て維持されることを Gate に据えたのはこのため

### 懸念② identity 非依存の統合には別のリスクがある

「identity が確定しなくても統合する」は fallback を減らすが、**identity が確定しない = 何が鳴っているか分からない状態で統合する**ことでもある。

- PC集合・ベース・支持音の一致という**具体的な条件**を課すこと
- 「確定しないから統合する」ではなく「**別の証拠で同一と言える場合に限り統合する**」

### 懸念③ Track C は P4.4〜4.5 と同じ領域である

スコアリングと候補生成は、**3フェーズ非昇格になった領域**である。

- shadow から始め、rank 1 を変える判断は分けること
- b9/b13 を「追加できた」ことと「正しく選べる」ことは別。**後者を測ってから接続する**

### 懸念④ このファイル1本に最適化するリスク

fixture は1曲である。**ボサノバ 2-feel に特化した調整**にならないよう、既存コーパスの回帰を必ず併走させる。

**特に Track A は「変化を減らす」方向にしか働かない**(P5.24 提案書 §11 懸念②と同じ性質)。False Merge Rate を最優先の安全指標として維持すること。

## 9. やらないこと

- P5.24 の Global 推定を削除すること(**Local を追加する**)
- スコアリングの直接変更(Track C は診断から始める)
- テンプレート総数を増やす形での語彙拡張
- 量子化・タイミング補正
- Voice 役割推定の変更(Phase 5.21 の範囲)
- 保存済みデータの遡及修正
- `Amaj9/B` → `Amaj7/B` の規約を必須とすること(優先度低)

## 10. 位置づけ

P5.24 は「演奏の打鍵と和声の変化を分離する」機構を作ったが、**実データでは fallback していた。**

本提案はその機構を実際に発火させ、あわせて実データで初めて優先度が確認された語彙・表記の問題を扱う。

**8小節中3小節の誤りが、すべて同一原因(小節内のベース経過音)である。** ここを解くことが最短距離である。
