## Text capacity audit

The 4096 / 12 / 48 envelope is duplicated at these production boundaries:

- `src/domain/textProgression.ts` exports all three parser constants and uses
  them for rejection plus bounded invalid-result materialization.
- `src/domain/textProgressionDraft.ts` independently rejects `result.bars > 12`
  and contains 1-to-12 contract comments.
- `src/store/vaultStore.ts` independently enforces at most 48 chords, absolute
  end at beat 48, and `bar <= 12` in the public Text save adapter.
- `src/components/capture/TextProgressionCapturePanel.tsx` hard-codes the
  12-bar / 48-token help and Japanese 4096 / 12 / 48 diagnostics.

Tests coupled to the current envelope live in `textProgression.test.ts`,
`textProgressionDraft.test.ts`, `vaultStore.test.ts`, the Capture panel tests,
and Text downstream/e2e tests. No textarea `maxLength` or shared security intake
budget enforces 4096. The global metadata budget is separate, so 8192 can be
changed locally without bypassing a shared security contract.

The exact path is:

`parseTextProgression` → `createTextProgressionDraft` →
`textProgressionDraftSavePayload` → Vault store Text adapter and save-safe
timeline validation → JSON repository reload →
`buildProgressionVoicingPracticeHandoffFromVault` → five detached snapshots.

The generic Manual Draft/range/candidate helpers do not impose a 12-bar bound.
The Stage01 seam must replace only the Text-specific duplicated bounds and keep
Chord Context's existing supported section lengths independent.

## Current layout audit

The current loaded layout is mode controls → CURRENT/NEXT (Learn/Recall inside
NEXT) → resolution/detail/keyboard → transport → wrapping progression strip.
The approved order instead places display controls at the top and the timeline
between CURRENT/NEXT and details.

Current timeline entries are non-interactive `span` elements in a wrapping flex
row. Width and height are content-driven; long labels and timing text can change
geometry. Current state only changes color/border today, but future audition and
playhead states need an explicit fixed 92px by 46px button contract, a local
horizontal viewport and no duration-based width.

## Resolver and audio audit

- `resolveProgressionPracticeVoicings` is the single family resolver. Source and
  Custom consume only detached exact pitches and fail closed; Lesson modes use
  the existing approved candidates.
- The current-code button passes the resolved MIDI notes to the transport's
  idle-only `audition`; timeline cards are not currently actionable.
- Full transport already schedules one resolved voicing attack at every event
  boundary unconditionally. This is effectively the future reference-sound ON
  path; Stage03 should gate this owned path rather than build another engine.
- Schedule IDs, PolySynth/click synths, pending starts and visual callbacks are
  owned by generation/projection epochs. Pause disposes instruments, Resume
  recreates and re-articulates, Restart reuses schedules after cleanup, and Stop
  clears owned schedules/resources.
- View effects and source/mode changes call `stop()` and invalidate stale async
  callbacks. Existing lifecycle stress tests cover long running and rapid cycles.

The new reference checkbox can remain `useState(true)` session state in the
Voicing Loop view and be passed into the existing transport. Extending the
versioned general voicing preferences is unnecessary and would widen storage
scope. No Vault schema/fileVersion change is needed.
