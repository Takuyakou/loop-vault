# P5.31 Design

## 1. Product framing

P5.31 is not “support ReChord the website.” It is:

> Accept the useful score notation that users copy from ReChord, normalize it
> deterministically into Loop Vault's existing chord/timing model, and let the
> existing save/practice pipeline do the rest.

The implementation must stay source-agnostic. “ReChord-compatible” is a parser
compatibility target, not a network integration.

## 2. Parsing pipeline

Preferred architecture:

```text
raw text
  ↓
line normalization / comments
  ↓
bar segmentation (`|`)
  ↓
cell/control lexical scan outside parentheses
  ↓
bounded candidate segmentation per bar
  ↓
existing chord parser validation
  ↓
unique parse or fail-closed diagnostic
  ↓
normalized Text progression model
  ↓
existing CaptureDraft adapter
```

Do **not** create a second chord parser.

### 2.1 Existing explicit syntax has priority

Existing Loop Vault syntax such as:

```text
| Dm7 G7 | Cmaj9 | Am7 |
```

must preserve its current meaning.

### 2.2 Root/type whitespace

ReChord examples include:

```text
A m7
G 7
F M7
C add9
```

Whitespace cannot therefore be treated as an unconditional chord delimiter.

Use bounded grouping of whitespace-separated lexemes and validate candidate
groups with the existing chord parser.

### 2.3 Compact adjacency

Examples:

```text
C9B7(#9,#5)
Em9Db7(#9)
Am9Am9/C
```

The tokenizer must search bounded segmentations that consume the entire bar.
Root-looking characters may propose boundaries but may never decide validity by
themselves.

Rules:

- never split inside `(...)`;
- never split the slash-bass suffix `/X`;
- preserve accidentals with roots;
- use the existing chord parser as the validity oracle;
- max accepted bar cell count remains 1 / 2 / 4;
- if multiple non-equivalent complete parses survive, fail closed and ask for
  spaces;
- if exactly one identity-equivalent parse survives, accept deterministically.

A greedy regex-only tokenizer is forbidden.

## 3. ReChord control cells

A **cell** is one rhythmic subdivision selected by the number of cells in the bar:

- 1 cell => 4 beats
- 2 cells => 2 beats each
- 4 cells => 1 beat each

No 3-cell auto-quantization.

### `%` — re-strike

- Requires a previous chord identity.
- Creates a new attack of that same chord at this cell boundary.
- It is not `=`.

### `_` — rest

- Produces silence for the cell.
- The musical clock continues.
- Reference sound must remain silent.
- Keyboard highlight must clear for the rest span.
- It must not fabricate a chord identity.

### `=` — hold

- Extends the immediately preceding sounding chord through the cell.
- Creates no new attack.
- Valid at a new bar if the preceding bar ended with a sounding chord.
- Invalid after a rest or at score start.
- May create a chord duration spanning a bar line.
- The current audio/transport path must honor “no re-attack”.

Official-style example:

```text
E 7%_A m7|=G
```

Expected 4/4 interpretation:

```text
bar 1:
  E7    beat 1      attack
  %     beat 2      E7 re-attack
  _     beat 3      rest
  Am7   beat 4      attack

bar 2:
  =     beats 1-2   hold Am7, no attack
  G     beats 3-4   attack
```

The Am7 sounding duration is therefore 3 beats total across the bar line.

## 4. Chord notation normalization

P5.31 must first test what the existing parser already accepts. Add only the
minimum aliases/normalizations needed by the accepted compatibility target.

Required fixtures include:

- `BbM7`, `CM7`, `Cmaj7`, `C△7`, `CΔ7`
- `Cm7`
- `Caug`
- `Csus2`, `Csus4`
- `Cadd9`, `Cadd11`
- `Cdim`, `Co7` where existing parser semantics make this unambiguous
- `C7(b9)`, `C7(#9,#5)`, `C7(b9,#11,b13)`
- `Comit3` if supported by the existing chord identity model
- `Am9/C`, `Dm7/G`

Do not blindly adopt every historical alias.

Example: historical ReChord/chord-translator material treated `C#5` as an
augmented-C spelling. In modern chord text, `C#5` is ambiguous with a C-sharp
power-chord-like spelling. P5.31 must not silently redefine such ambiguous text.
Prefer explicit `C(#5)` / `Caug` or an error.

## 5. Left-hand slash chords

The parser and the Lesson voicing engine are separate concerns.

P5.31 must preserve:

```text
Am11/B
```

as a slash-bass chord identity even if the Lesson Left-hand rule remains
unsupported.

Stage00 must inspect:

- the locked P5.27 Lesson Rule Table;
- lesson-source documentation already present in the repo/project;
- the shared Basic/Left-hand generators;
- current unsupported/failure reasons.

The subsequent [human product approval](contracts/11-human-approved-product-decisions.md)
selects **Upper Structure + Separate Slash Bass**. Resolve `X` through the existing
Left-hand lesson rules unchanged, retain identity `X/Y`, represent `Y` as separate
Bass reference, and combine them for reference/card/model playback. Only upper
notes are practice targets. Keyboard roles distinguish them. This is not evidence
that a teacher taught the slash rule.

Forbidden:

- drop `/B` and pretend the chord is `Am11`;
- silently switch to Basic/Shell/Auto;
- generic “jazz” guess not grounded in the lesson rule source.

If the upper structure itself is unsupported, preserve fail-closed behavior and
a compact honest diagnostic. Do not fall back to Basic, Source MIDI, or Custom.

## 6. Unsupported diagnostic aggregation

Current repeated messages such as:

```text
Am11/B: 未対応の規則
Am11/B: 未対応の規則
```

should be aggregated when the reason and normalized chord identity are equal:

```text
再生できないコードがあります
Am11/B ×2 — Left-hand未対応
```

Do not collapse distinct failure reasons.

## 7. Protected P5.30 surfaces

No redesign:

- sidebar/direct Voicing Loop entry;
- current progression picker/list behavior;
- CURRENT/NEXT;
- slim fixed-size progression cards;
- moving playhead;
- card click = audition only, not seek;
- centered keyboard;
- Learn/Recall;
- reference-sound checkbox;
- single musical clock;
- Pause/Resume/Restart/Stop;
- no scoring.

Any P5.31 UI addition must be minimal and use existing product visual language.
