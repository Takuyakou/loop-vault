# P5.32 Design

## 1. Core model

P5.32 does not choose the chord voicing.

It receives the already resolved voicing:

```ts
type FingeringInput = {
  hand: "right" | "left";
  midiPitchesAscending: number[];
  chordIdentity?: SafeChordIdentity;
  voicingFamily: "source-midi" | "custom" | "basic-shell" | "basic-full" | "full-shell" | "left-hand";
  previous?: ResolvedVoicingOrTimelineState;
  next?: ResolvedVoicingOrTimelineState;
};
```

The fingering engine returns metadata only:

```ts
type SuggestedFingering = {
  fingersAscending: number[];
  source: "user" | "suggested";
  reasonCodes: string[];
};
```

It must never modify pitch, octave, chord identity, slash bass, duration, or
timeline boundaries.

## 2. Finger numbering

Standard:

```text
1 thumb
2 index
3 middle
4 ring
5 little
```

Pitches are always sorted low → high.

For simultaneous notes:

- right-hand finger numbers must be strictly ascending low → high;
- left-hand finger numbers must be strictly descending low → high.

## 3. Bounded candidate generation

For N distinct simultaneous keys, N must be 1..5 for single-hand suggestion.

Candidate generation is intentionally tiny:

- choose N fingers from `[1,2,3,4,5]`;
- sort ascending for RH;
- reverse for LH.

Maximum candidates:

```text
C(5,1)=5
C(5,2)=10
C(5,3)=10
C(5,4)=5
C(5,5)=1
```

No exponential search over arbitrary finger sequences.

If >5 distinct simultaneous physical keys are requested for one hand:

- do not invent a fingering;
- show `おすすめ運指なし`;
- exact voicing remains playable/auditionable as before.

## 4. First-choice priors from the supplied guide

These are **priors**, not universal truth.

### Triads

| Shape | Right | Left |
|---|---|---|
| root position | 1-3-5 | 5-3-1 |
| first inversion | 1-2-5 | 5-3-1 |
| second inversion | 1-3-5 | 5-2-1 |

Apply shape-specific priors only when the chord/voicing can be safely recognized
as that triad inversion. Otherwise use generic candidates.

### Four-note chord / rootless starting points

- right: `1-2-3-5`
- left: `5-3-2-1`

Alternative candidates remain available.

### Two-note guide-tone shell

- right: `1-5`
- left: `5-1`

### Three-note left-hand shell

- left: `5-3-1`

## 5. Spacing-fit heuristic

The guide repeatedly says a starting fingering may need to change based on the
actual spacing and neighboring chord.

P5.32 may use a deterministic **spacing-fit heuristic**, not a claim of human
ergonomic optimality:

1. normalize physical key positions of the chord from 0..1;
2. normalize chosen finger positions from 0..1 for the current hand;
3. penalize large mismatch between those normalized patterns.

This helps distinguish, for example, `1-2-3-5` from `1-2-4-5` without using a
hard-coded hand-size model.

Do not add a hard rule that thumb may not play a black key.

## 6. Progression-aware transition ranking

Each event has at most 10 candidates.

For candidate A → B, use bounded deterministic costs such as:

- same physical pitch + same finger: strong continuity bonus;
- same physical pitch + different finger: allowed, small cost;
- same finger moving to another pitch: cost proportional to semitone/key distance;
- missing/appearing finger: small transition cost;
- deviation from the family/shape prior;
- spacing-fit cost.

Do not make common pitch + same finger mandatory.

### Cyclic Voicing Loop

The progression loops endlessly, so the last → first transition matters.

Use cyclic dynamic programming:

1. enumerate each candidate for event 0;
2. DP through the remaining events;
3. add final-event → event-0 transition;
4. select minimum deterministic total cost;
5. stable tie-break by canonical candidate ordering.

Complexity is bounded by:

```text
O(events * candidates^2)
```

With ≤128 chord events and ≤10 candidates, this is trivial enough for the app,
but Stage04 must benchmark it anyway.

## 7. P5.31 control cells

If present in the integrated base:

- `%` / re-strike:
  - reuse the same fingering as the immediately preceding resolved chord;
- `=` / hold:
  - inherit the sounding chord's fingering;
  - no new candidate or UI “change”;
- `_` / rest:
  - no chord target;
  - no fingering target;
  - keyboard clears as the existing P5.31 contract requires.

## 8. Slash-bass handling

Respect the integrated P5.31 policy.

If `Left-hand` uses:

> Upper Structure + Separate Slash Bass

then:

- slash chord identity remains intact;
- Bass reference remains visible/audible according to P5.31;
- P5.32 fingering applies only to the **actual Left-hand target notes**;
- do not assign a fake finger to a bass reference that is not part of the target
  voicing.

For other modes, if slash bass is physically included in the exact resolved
single-hand voicing, it participates like any other physical pitch.

## 9. User override

Preferred key:

```text
physicalVoicingSignature = hand + sorted unique absolute MIDI pitches
```

Why exact physical pitch, not chord name:

- same chord name can have many voicings;
- same physical keys can serve different chord functions but have the same
  fingering ergonomics.

User override:

- stores exact finger array for the exact physical voicing signature;
- wins over Suggested Fingering;
- is visibly labelled `自分の運指`;
- can be reset to automatic suggestion.

Do not transpose a saved override automatically to another register/key in
P5.32.

## 10. UI

Approved mock direction:

- all six integrated Voicing modes visible;
- hand selector:
  - Source MIDI / Custom / Basic Shell / Basic Full / Full Shell: select only an existing resolved hand target;
  - Left-hand: L locked;
- CURRENT:
  - Chord
  - Pitch
  - Degree
  - Finger
- NEXT:
  - same, smaller;
- keyboard:
  - active pitch
  - `R1` / `L5` etc.;
- checkbox:
  - `おすすめ運指`;
- actions:
  - `運指を編集`
  - `この運指を保存`
  - reset when personal override exists.

Do not resize progression timeline cards.

## 11. No scoring

MIDI input does not need to detect which physical finger the user used.

P5.32 has no:

- correct/incorrect fingering;
- score;
- streak;
- mastery;
- XP;
- hand tracking.

The purpose is decision support and repetition.
