# P5.33 Design

## 1. Separate the axes

The old product accumulated different concepts under one “Voicing” selection.

P5.33 introduces explicit domain axes.

```ts
type VoicingSource =
  | "lesson-rules"
  | "source-midi"
  | "custom";

type StudyCategory =
  | "teacher"
  | "core"
  | "color"
  | "open";

type CoverageMode =
  | "literal"
  | "performance-reduction"
  | "creative-enrichment";

type Provenance =
  | "teacher-evidence"
  | "external-theory"
  | "analysis-proposal";
```

`RuleFamilyId`, `VariantId`, and context are separate types.

Do not compress them into a giant enum.

## 2. Candidate output

A generated practice candidate needs enough data to explain itself.

```ts
type PracticeVoicingCandidate = {
  chordIdentity: CanonicalChordIdentity;
  source: "lesson-rules";
  studyCategory: StudyCategory;
  ruleFamilyId: string;
  variantId: string;

  leftHand: ResolvedHandTarget;
  rightHand: ResolvedHandTarget;

  coverageMode: CoverageMode;
  omittedDegrees: DegreeLabel[];
  addedDegrees: DegreeLabel[];

  topNote?: {
    midi: number;
    degree: DegreeLabel;
    role: "fixed-melody" | "top-candidate" | "voicing-top";
  };

  provenance: ProvenanceSummary;
  confidence: RuleConfidence;
  reasonCodes: string[];
};
```

Suggested fingering is resolved after this object exists.

## 3. Hard harmonic accounting

For each rule candidate, compute and test:

```text
original reference pitch classes
actual sounding pitch classes
omitted pitch classes/degrees
added pitch classes/degrees
external sounding requirements
```

### Literal

No unlisted note may be added.

### Performance Reduction

May omit a declared optional/allowed degree.
Must expose `OMIT`.

### Creative Enrichment

May add color only when the user intentionally enters a category/rule that
allows enrichment.
Must expose what was added.
Never masquerade as Literal.

## 4. Slash chords

`X/Y` keeps:

```text
upper/root identity = X
specified bass = Y
```

Degree labels continue to use the upper/root unless an analysis field explicitly
says otherwise.

### First-wave expected examples

`Eadd9/F#`

```text
LH F# = 9
RH E G# B = 1 3 5
coverage = Literal
```

`Dadd9/E`

```text
LH E = 9
RH D F# A = 1 3 5
coverage = Literal
```

`Am9/C`

```text
LH C = b3
RH A B E G = 1 9 5 b7
coverage = Literal
```

`Am11/B`

```text
LH B = 9
RH A C D G = 1 b3 11 b7
omit = 5
coverage = Performance Reduction
```

`Gmaj9/A` compact

```text
LH A = 9
RH F# G B = 7 1 3
omit = 5
coverage = Performance Reduction
```

`Gmaj9/A` full

```text
LH A = 9
RH D F# G B = 5 7 1 3
coverage = Literal
```

These examples are research promotion fixtures, not permission to apply one
generic slash algorithm to every chord.

## 5. Teacher category

Teacher rules are provenance-sensitive.

Teacher source evidence directly supports role structures such as:

```text
LH Root + seventh-family tone
RH third + Melody
```

and certain dominant LH color structures.

But exact octave, fingering, and a Melody note may be research proposals.

Therefore:

- never label an app-selected top note as teacher-provided Melody;
- use `Top Candidate` when the app chooses the note;
- use `Melody` only when the input/context actually supplies a melody;
- expose provenance in developer/report data even if the normal UI stays compact.

## 6. Core category

Core is for chord identity / composition skeleton:

- Bass + guide tones
- slash literal structures
- characteristic-tone cores
- m7b5
- dim7
- 6/9
- sus

Core must favor explainability over “fancy” color.

## 7. Color category

Color intentionally adds/foregrounds tensions:

- teacher LH 9/13 structures when context is valid
- upper-structure dominant examples
- altered-dominant color

If the candidate changes a Literal pitch-class set, `Creative Enrichment` must
be visible.

## 8. Open category

First-wave Open covers:

- two-handed extended spread
- open triad
- Drop 2

Drop 2 transforms the specified upper 4-note group only.
A fixed/slash/external Bass is not blindly included in the transform.

Quartal / So What are deferred until separately promoted.

## 9. Candidate variants

One chord may have more than one valid candidate.

Example:

```text
Gmaj9/A
candidate 1: compact / Reduction
candidate 2: full / Literal
```

The upper UI displays:

```text
候補 1/2
```

Candidate switching is session-local in P5.33 unless Stage00 finds a safe
existing persistence path and the stage contract explicitly authorizes reuse.

No schema change.

## 10. Progression-aware selection

Candidate ranking considers:

- pitch movement;
- common tones;
- hand span;
- register;
- top-note continuity;
- rule/category preference;
- coverage preference;
- loop last → first transition.

Minimum movement is not the only truth.

The ranker selects among already valid candidates. It must never invent notes
just to lower motion cost.

## 11. UI — adopted top section + keyboard/transport normalization

P5.33 changes:

- SOURCE
- STUDY
- DISPLAY
- Current
- Next
- Beat/Position/Loop
- Keyboard geometry consistency
- Transport sizing/density

Protected:

- existing production sidebar
- existing production PROGRESSION geometry/behavior

The lower half of the research HTML mock is **not** a visual contract. Keyboard
and Transport changes come from the user's later production screenshot review,
not from that mock.

### Keyboard contract

Voicing Loop uses one stable visual keyboard:

```text
88 keys
A0–C8
same key positions
same width
same height
same octave labels
```

for every:

- Lesson Rules study category;
- Source MIDI;
- Custom;
- candidate variant.

Mode/source changes may change only:

- highlighted pitches;
- LEFT/RIGHT assignment;
- finger badges;
- pressed/pedal state.

They must not change keyboard scale, crop, zoom, start/end note, or overall
geometry.

The keyboard container should tightly fit the physical keyboard plus its small
legend/input row. Large unused black space below the keys is a layout defect.

### Transport contract

Freed keyboard dead-space height is reassigned to the Transport surface.

Desktop target:

- Transport row roughly 48–56 px where existing design tokens allow;
- Start button roughly 38–42 px tall and visually primary;
- secondary controls roughly 34–38 px tall;
- clearer hit targets without adding page height.

This is presentation-only. No clock/audio/transport state-machine change.

## 12. No-scroll desktop contract

Normal desktop Voicing Loop must require no page scroll.

Do not solve P5.33 by making the adopted top section taller.

Do not solve keyboard consistency with horizontal/vertical scrolling or
mode-specific zooming on normal desktop.

The screen-height budget should be reclaimed in this order:

1. remove keyboard dead space;
2. reduce redundant padding/gaps;
3. keep Current/Next compact;
4. spend part of the reclaimed height on a more usable Transport row.

Toolbar and Current/Next must remain compact.
