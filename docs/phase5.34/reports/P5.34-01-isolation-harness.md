# P5.34-01 — Isolation Harness

- Binding commit: `2c881ff` (P5.34-00) → this stage
- Evidence classification per Contract 02.

## What was built

A deterministic, shadow-only diagnostic harness in `scripts/p534/`:

- `isolationCore.ts` — pure functions: meter view, meter-independent segmenter,
  onset snap, PPQ-normalized sweep, full-path instrumentation.
- `fixtures.ts` — deterministic synthetic MIDI builders (S01–S07 pitch sets +
  generic `buildMidi` / `chordFixture`).
- `run-isolation.ts` — CLI runner (vite-node), emits privacy-safe aggregates.
- `isolationCore.test.ts` — 8 tests.

No product code changed; no feature flag added.

## Instrumented path

`source → parseMidi/preparedData → weighted windows → per-window chord →
smoothed timeline → block candidates → formatted text`.

Privacy-safe counts recorded at each stage:

- `windowCount`
- `timelineItemCount`
- `blockItemCount`
- `occupiedBarCount`
- `formattedBarCount`
- `dashCount`

These locate exactly where the ~65-bar / many-dash shape is created: the
window grid is the shared core of `legacy-v1` and `phase4-v1` (`buildWeightedWindows`),
and the bar/dash counts derive from the meter-driven bar/beat labels.

## Variant definitions (corrections applied)

- **A** — original meter + current behavior (`buildWeightedWindows` on parsed data).
- **B** — diagnostic 4/4 meter view only (`withMeterView`). Only `timeSignature`
  and the meter-derived `totalBars` change; notes, `ticksPerBeat`/PPQ, tempo,
  pitch, onset, duration, velocity are all identical (asserted by reference +
  deep equality). A and B use the exact same analyzer/options.
- **C** — genuinely meter-independent (`buildMeterIndependentWindows`). The grid
  extent is derived from the unchanged source-note extent (`sourceExtentBeat`),
  and `timeSignature`/`totalBars` never define a harmonic window. Meter is kept
  only as diagnostic metadata; the beat-position factor has no bar-start bonus.
- **D** — C plus a bounded PPQ-normalized onset sweep
  (`0, P/96, P/48, P/24, P/16, P/8`, rounded and de-duplicated). Each point is a
  transient onset snap; no threshold is promoted.

## Re-strike classification

Re-strike is treated as **not a direct boundary primitive**: it does not create
a boundary on its own, but it can still affect attack/onset evidence. The
harness preserves this by not special-casing re-strikes in segmentation.

## Onset (D) caveat

The default chord profile already uses duration overlap
(`overlaps` in `legacy.ts`), not onset-exact grouping. D therefore records which
exact-onset code path changes the result: onset snapping only matters where the
overlap predicate or an onset-keyed path flips, and must not be assumed globally
causal. (The only onset-exact paths in the codebase are `groupOnsets` in
`segmentation.ts` and `strongestByOnset` in the shadow evidence — both outside
the default legacy/phase4 window path.)

## Tests (8 passing)

- `withMeterView` does not mutate the source and changes only meter-derived fields.
- A and B share identical note events.
- Meter-independent segmenter derives extent from source notes (not `totalBars`).
- `snapOnsets` never mutates the source notes.
- `onsetSweepTicks` is deterministic and de-duplicated.
- `instrument` is deterministic across repeated runs.
- `instrument` captures 1/4-vs-4/4 fragmentation as bar/dash counts.
- Output is privacy-safe (chord labels + numbers only; no paths/names).

## Scope note on labels

The harness infers chord labels with the legacy default matcher (`matchWindow`),
which does not apply `phase4-v1` quality-evidence scoring. Segmentation counts
(windows / bars / dashes) are unaffected; identity/quality-evidence comparison
is a separate P5.34-02 concern (separate segmentation from identity).
