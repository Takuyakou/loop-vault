## A/B invariants

`meterIdentityAB(data, roles)` compares two diagnostic views of the SAME source:
A = source meter as parsed (LF-MIDI-001 = 1/4), B = a 4/4 view via
`withMeterView(data, 4, 4)` (notes untouched). Only the diagnostic meter/grid view
differs — pitch, startTick, duration, velocity, PPQ, tempo, source ordering,
analyzer path, candidate vocabulary, and ranking code are identical, and the window
WIDTH stays 2 beats (§11). `buildWeightedWindows`/`matchWindow` are consumed
read-only. Source immutability and determinism are asserted by tests
(`meterIdentityAB.test.ts`).

## Structural window-membership comparison (Level A)

For every window index the tick range is `[i·2·PPQ, (i·2+2)·PPQ)` — a "beat" is
`ticksPerBeat` ticks, **independent of meter** — so window bounds and membership do
not depend on the meter tag.

| Metric | Result (LF-MIDI-001) |
|--------|----------------------|
| window count A (1/4) | 33 |
| window count B (4/4) | 34 (one extra **empty** trailing window; totalBeats rounds up to a 4-multiple) |
| `membershipAllEqual` | **true** (0 non-empty windows with differing membership) |

## Histogram comparison (Level A)

| Metric | Result |
|--------|--------|
| `histogramAllEqual` (bit-equal) | **false** |
| `histogramAllProportional` (equal after per-window normalization) | **true** |
| distinct per-window scales (non-empty) | **{1.000, 0.800}** |

The only histogram difference is a **uniform per-window scalar**: in 1/4,
`beatPositionFactor(startBeat, 1)` is `1.5` for every window; in 4/4,
`beatPositionFactor(startBeat, 4)` is `1.5` on windows at `startBeat % 4 == 0` and
`1.2` on windows at `startBeat % 4 == 2` (ratio `1.2/1.5 = 0.8`). Because the factor
multiplies the whole window uniformly, it cancels in `scoreTemplates`
(`hit/total`, `outside/total`, `rootWeight = histogram[root]/total`, and the argmax
of `bassHistogram` are all scale-invariant). `bassHistogram` argmax is likewise
unchanged.

## Candidate presence & bass/root/slash separation

- **Candidate ranks are meter-invariant:** because the per-window histogram scale
  cancels, the entire candidate ranking (not just top-1) is identical in A and B.
  Whatever rank the intended/equivalent candidate holds, the meter view does not
  move it — so meter normalization cannot be the lever that promotes a correct
  candidate. (Oracle truth is not fed into ranking; §12/§13/§17 held.)
- **Structural bass / root / slash all A==B:** `bassPc` unchanged (G/B), top-1 root
  unchanged, slash bass unchanged. Consistent with P5.34/P5.35 — the structural
  bass estimate is stable; the wrong-root label is not a bass-extraction failure.

## P5.34 downstream fragmentation re-check (separate from identity)

`withMeterView(1/4 → 4/4)` changes `totalBars` from **65** to **17** (derived:
windowCountB = 34 → totalBeats_B = 68 → 17 bars of 4/4). This is the P5.34
downstream family: fewer bars/blocks/dashes in the 4/4 view. It is a
**formatting/block-structure** effect and is **classified separately** from the
harmonic-identity effect above — "bars changed" is not taken as "chord analysis
changed" (§9). The 33 shared 2-beat chord identities are unchanged regardless.

## Answers (Q1–Q6)

- **Q1 — does 1/4→4/4 change legacy 2-beat window membership?** **No.** Membership
  is identical for every non-empty window (bounds are meter-independent tick
  ranges). B has one extra empty trailing window only.
- **Q2 — does the histogram change?** Only by a **uniform per-window scalar**
  (1.5 vs 1.2 `beatPositionFactor`); not bit-equal, but proportional, and the scale
  cancels in scoring.
- **Q3 — do wrong-root top-1 / ranks change?** **No.** All four targets keep their
  exact label and bass; the full ranking is meter-invariant.
- **Q4 — do structural bass / root / slash change?** **No.** All A==B.
- **Q5 — same causal mechanism or separate-but-co-occurring?** **Separate but
  co-occurring.** 1/4 meter drives downstream bar/block/text fragmentation
  (65→17 bars), but the wrong-root *identity* failure is independent of the meter
  tag — it is produced by the fixed 2-beat evidence aggregation itself.
- **Q6 — P5.36-03 priority?** **Sub-window / attack-state isolation** of the fixed
  2-beat aggregation. Meter normalization is de-prioritized (it does not move
  identity), and no hidden meter-dependent scoring path exists (Q3/M3 ruled out).
