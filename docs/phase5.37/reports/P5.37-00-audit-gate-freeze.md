## Audit answers (Q1–Q12; read-only, repo-truth)

1. **Where is 4/4 enforced?** `src/domain/midi/localHarmonicStateIntegration.ts`:
   `prepareLocalHarmonicStateAnalyzerOptions` returns
   `{applied:false, reason:"unsupported-meter"}` when
   `production.data.timeSignature !== "4/4"` (line 82). Also `meter:[4,4]` is
   hardcoded in the shadow input (line 90) and in `buildProductionInput` (line 189:
   `meter:[4,4], totalBeats: data.totalBars * 4`); the type
   `P526LocalHarmonicStateShadowInput.meter` is `readonly [4,4]`; boundary logic
   uses `boundary.beat % 4` (line 108). **Verified live:** flag ON on the 1/4
   fixture returns `reason = "unsupported-meter"`, `applied = false`.
2. **Algorithmically necessary or historical/defensive?** **Historical/defensive.**
   The note evidence is already absolute-beat based (`startBeat = startTick /
   ticksPerBeat`, `durationBeats = durationTick / ticksPerBeat`, line 184–185),
   independent of the meter tag. The 4/4 assumptions are the `totalBeats = totalBars
   * 4` formula, the `meter:[4,4]` value/type, and `% 4` bar-phase logic — all
   parameterizable by `beatsPerBar`.
3. **Which calculations depend on beats/bars/meter?** `totalBeats = totalBars * 4`
   (should be `* beatsPerBar`); `meter:[4,4]`; bar-phase `boundary.beat % 4`;
   `localPeriods = Array(totalBars)`; `local.bars` per-bar periods; `finestPeriod` /
   `beatsPerWindow` derived from local periods. Note onsets/durations do **not**.
4. **Can it operate from absolute beats/ticks without bar assumptions?** **Yes** —
   the note model already is absolute-beat; generalizing requires threading the real
   `beatsPerBar(timeSignature)` (=1 for 1/4) into `totalBeats`, the `meter`
   descriptor, and the bar-phase modulo, instead of the constant 4.
5. **OFF exact-legacy path?** `enableLocalHarmonicStateConsolidation !== true` →
   `{applied:false, reason:"flag-off"}` (line 71); every unsupported/ambiguous case
   (`unsupported-analyzer-mode`, `invalid-input`, `unsupported-meter`,
   `legacy-fallback`) returns the caller's exact `options` for legacy analysis.
   Robust OFF = exact legacy.
6. **Smallest shadow seam?** The estimator chain behind the eligibility function —
   `estimateP524BassLane` → `estimateP524HarmonicRhythm` → `buildBeatCells` →
   `estimateP526LocalHarmonicStateShadow` → `projectLocalStates` — can be exercised
   in a shadow harness (`scripts/p537/`) with a meter-independent `totalBeats` /
   `meter` descriptor, without touching production, to demonstrate non-4/4 local
   states.
7. **Local-state output deterministic?** Structurally yes (pure estimators; notes
   sorted by `compareShadowNotes`; bounded operation counters in `diagnostics`).
   Confirmed: two default `analyzeMidi` runs produce identical labels. P5.37-01 adds
   an explicit determinism test.
8. **Existing tests covering 4/4?** `localHarmonicStateIntegration.test.ts`,
   `harmonicStateConsolidation.test.ts`, `harmonicState/*` tests, `segmentation.test.ts`.
9. **Missing non-4/4 tests?** No 1/4 (or general non-4/4) local-state test exists —
   the gap P5.37-01 fills.
10. **LF-MIDI-001 through shadow without mutation?** Yes — `buildProductionInput`
    reads via `parseMidi` / `preparedData` and copies notes (`.map(...)`); no
    mutation. Gate H (source fidelity) is enforceable.
11. **Reusable P5.36 hard negatives?** All of `scripts/p536/fixtures.ts`
