**Type D (truly 4/4-only): none.** The note evidence is absolute-beat
(`startBeat = startTick/ticksPerBeat`), so the algorithm is generalizable — but the
**Type-B bar-position priors must not be blind-replaced** (§4): with
`beatsPerBar = 1` for 1/4, `beat % 1 === 0` is true for every integer beat, so
`structuralBarBoundary` and `atBarBoundary` become always-true. That does not
directly over-split (the split still requires `persistentBassChange` — a genuine
held-bass difference — so held/rolled/arpeggiated chords with a stable bass are not
split), but it silently removes the bar-position gate, which must be a deliberate,
tested design choice (S2), not an accident.

## The block (§6 / §8 / §29)

A reuse-based, parity-provable shadow is **not achievable on the existing
architecture** without changing production, because:

1. **No meter knob on the public surface.** `estimateP526LocalHarmonicStateShadow`
   reads a **private module constant** `const beatsPerBar = 4` (not `input.meter`),
   and rejects non-4/4 via `hasUnsupportedMeter`. Passing `input.meter = [1,4]`
   (even via cast) is rejected and would not change the internal `beatsPerBar`.
2. **The generalizable logic is private.** `buildBeatCells` (+ `matrix`,
   `applyInterval`, `sweepCoverage`, `metricStrength`), `decideBoundary`,
   `split`/`merge`, the consolidation loop, and `projectLocalStates` are all
   un-exported (~410 lines in `localHarmonicStateShadow.ts` plus the integration
   helpers).
3. **§9's mandatory 4/4-parity gate requires a faithful replica** of exactly these
   private internals to compare "current implementation vs generalized shadow" on
   boundaries / merge-split decisions / state count / identities / reason codes.
   A lighter shadow (reusing only the exported evidence estimators + a compact
   `decideBoundary` re-implementation) would NOT reproduce production's
   `buildBeatCells` cell evidence, so S0 parity could not be proven.

Therefore the only two ways forward both cross a line Stage-01 reserves for
explicit authorization:

- **Option (b) — RECOMMENDED: minimal, behavior-preserving production
  parameterization.** Make `beatsPerBar` a parameter (default `4`); thread the real
  `beatsPerBar(timeSignature)` only when the flag is ON; relax the Type-C meter
  gates behind the flag; **neutralize** the Type-B bar-position prior for non-4/4
  (S2) rather than `% beatsPerBar`. Default 4/4 callers get **bit-identical**
  behavior (parameter defaults to 4, gates unchanged when flag OFF), and
  `OFF = exact legacy` is preserved. This is a production change, which §6/§29
  forbid unilaterally in Stage-01 → **STOP + report** (this document).
- **Option (a) — DISCOURAGED: fork ~410 lines** of private internals into
  `scripts/p537/` as a parity-guarded replica. Faithful-but-fragile duplication;
  §8 explicitly discourages re-implementing over reusing existing logic, and it
  creates a long-lived divergence liability. Not taken unilaterally.

Per §8 ("既存architecture上不可能なら明記してSTOP") and §6/§29 ("Production surface
変更が必要になる場合はSTOPして報告"), this stage stops here and reports rather than
forking or changing production.

## Recommended shadow policy (design frozen for review; not yet demonstrated)

The intended S2 policy for P5.37-02, contingent on Option (b) authorization:

- **Meter handling:** absolute-beat cells; `beatsPerBar = beatsPerBar(timeSignature)`
  for Type-A conversions only.
- **Boundary evidence:** the existing `decideBoundary` evidence — `persistent-bass-
  change`, `persistent-upper-change`, `same-pitch-material`, `stable-upper-
  structure`, pc-support, temporal-continuity, local-rhythm — all meter-independent.
- **Meter-position prior:** **neutralized** for non-4/4 (the Type-B
  `structuralBarBoundary`/`atBarBoundary` gate is not used to force or block splits
  when `beatsPerBar` ≠ 4); splits are driven by the musical evidence
  (`persistentBassChange` with held-bass persistence on both sides, etc.).
- **Fallback:** unchanged `legacy-fallback` / `unsupported-*` → exact legacy; flag
  OFF → exact legacy.
- **Reason codes:** existing `merge-same-state` / `split-structural-change` /
  `legacy-fallback` and the existing `P526BoundaryEvidence` set; no
  private-fixture-specific reasons.

This policy is **not** frozen for promotion yet (§26) because it has not been
demonstrated (blocked above). Freezing happens once the shadow can actually run.
