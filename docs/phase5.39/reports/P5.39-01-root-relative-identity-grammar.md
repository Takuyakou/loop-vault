## Shadow descriptor

`ShadowRootRelativeIdentity` contains:

```text
rootPitchClass
triad
seventh
extensions[]
alterations[]
omissions[]
bassPitchClass?
```

The two authorized Family-C archetypes are data templates, not root-specific
branches:

| archetype | upper identity | root-relative pitch classes |
|---|---|---|
| altered dominant / omitted fifth | major third + minor seventh + `#9` + `b13` + `no5` | `0,3,4,8,10` |
| dominant 11 / omitted fifth | major third + minor seventh + `9` + `11` + `no5` | `0,2,4,5,10` |

The representability catalog contains exactly 30 upper templates: the existing
21 production qualities, these two targets, their two with-fifth Stage00
hard-negative neighbors, and five individual dominant-alteration neighbors
(`b9`, `#9`, `#11`, `b13`, `#5`). It does not enumerate the cross-product of
extensions, alterations, and omissions. Formatter and Shadow parser both reject
identities outside this catalog, including arbitrary modifier powersets.

## Root-relative normalization

Observed pitches are reduced to unique pitch classes relative to the proposed
root, then sorted. Absolute MIDI register, octave, note order, and doubling do
not enter the identity key. A separate root-independent key proves that every
transposition of one archetype shares one semantic family.

Stage01 generates nine fixed transforms for every target/root: close ordered,
reversed, deterministic permuted, high register, octave spread, root doubled,
third doubled, seventh doubled, and extension/alteration doubled. Result:
`24 targets x 9 transforms = 216/216` exact Shadow matches.

## Omission model

`no3` and `no5` are explicit bounded descriptors. Normalization accepts an
omission only when the base triad normally contains that structural degree. For
example, `no3` on `sus4` is rejected rather than treating the already-absent
third as an omission.

The oracle removes a structural tone only when the target explicitly carries
the omission. A voicing that happens not to contain the fifth does not match the
corresponding complete identity, so absence is not silently promoted to `no5`.
Descriptors where an omitted base degree and an explicit modifier occupy the
same pitch class are rejected: the pitch-class oracle cannot honestly prove
both facts, and it never silently deletes the modifier.

## Extension and alteration model

Natural extensions are bounded to `6`, `9`, `11`, and `13`. Alterations are
bounded to `b9`, `#9`, `#11`, `b13`, and `#5`. Canonical output never uses
`alt`; it writes the actual facts, such as `G7(#9,b13,no5)` and `B11(no5)`.
Each single dominant alteration is supported across all 12 roots. The parser
rejects combinations outside the fixed catalog, such as an arbitrary
`b9 x #9 x #11 x b13 x #5 x no3 x no5` powerset. Since `b13` and `#5` share a
pitch class, pitch-class-only evidence reports those two readings as ambiguous
by contract instead of inventing a preference.

## Bass model

`bassPitchClass` is separate from the upper structure and excluded from the
root-relative family key. The full identity key retains it. Oracle calls receive
upper notes and bass separately; bass is never inferred from input order.

## Canonical key, label, and Shadow parser

Identity, display, and parsing are separate operations:

- `shadowRootRelativeKey` excludes root and bass for family comparison;
- `shadowIdentityKey` includes normalized root and optional bass;
- `formatShadowIdentity` emits deterministic explicit notation;
- `parseShadowChordLabel` reads only the bounded Shadow notation and delegates
  existing surface forms to the unchanged production parser.

Ordering follows the existing `chords.ts` tension order, restricted to the
Shadow alteration set, followed by `no3`, `no5`. Input order and duplicates are
canonicalized. Every target passes exact
`identity -> label -> Shadow parse -> identity`. Production parsing remains
unsupported for the 24 omission-sensitive target labels by design.

## Ambiguity policy

The primary representability oracle owns the bounded catalog; callers provide
only note evidence, optional root, and optional bass. It returns exactly
`REPRESENTABLE`, `NOT_REPRESENTABLE`, or `AMBIGUOUS_BY_CONTRACT`, plus explicit
reason codes. It covers the targets, their with-fifth neighbors, all five
individual-alteration neighbors, and simple/9th/11th/13th existing controls. If an unspecified root permits multiple
catalog identities (for example, a pitch-class set admitting both sixth and
minor-seventh readings), it reports contract ambiguity rather than forcing one.

The Shadow representability lookup is root-indexed. With a proposed root it

## Source fidelity and determinism

The oracle reads copied pitch values only. A source-note fixture carrying pitch,
start tick, duration, and velocity is deep-compared before/after normalization,
matching, resolution, formatting, and parsing. All fields remain unchanged.
Repeated key, label, parse, and ambiguity results are byte-identical.
