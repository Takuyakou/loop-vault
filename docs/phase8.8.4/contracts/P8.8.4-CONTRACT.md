# P8.8.4 CONTRACT

## 1. Scope

P8.8.4 owns:
- Standard/Extended Text Capture UI unification;
- transport interaction improvements;
- display/presentation consistency;
- compacting Standard-only detail/capability UI without deleting functionality.

It does NOT own:
- chord semantic/theory changes;
- defining-tone changes;
- external-site compatibility expansion;
- MIDI Analyzer/Core changes;
- Vault schema migration;
- Home/Vault/Progression/Bass Practice redesign.

---

## 2. No visual regression from P8.8.2/P8.8.3

Preserve:
- duration-proportional HarmonicSpan bands;
- authored reattack markers;
- hold rendering;
- rest/N.C. rendering;
- authored written spelling;
- source-positioned annotations/comments;
- raw erroneous bar visible in place;
- exact parser source-span linking;
- editor -> preview and preview -> editor linkage;
- 4 bars/row on normal desktop;
- current responsive behavior;
- ERROR / WARNING / PRACTICE LIMIT separation;
- save-blocking reason UX;
- long-chart support.

Never replace this with giant per-chord cards.

---

## 3. Common Text Capture shell

Refactor Standard and Extended onto one outer UI architecture.

Conceptually:

```text
CaptureView
└─ shared CaptureModeTabs: MIDI / テキスト
   └─ TextCaptureWorkspace
      ├─ Standard parser adapter
      └─ Extended parser adapter
```

Requirements:
- MIDI/Text tabs use the same placement/alignment as MIDI mode;
- remove duplicate/independent text-mode tab strip placement;
- Text Capture audition timbre selector (`ピアノ / エレピ`) is removed;
- fixed text confirmation audition continues through the P8.8.3 resolver;
- do not remove unrelated global sound settings.

---

## 4. Shared heading skeleton

Both modes use the same compact structure:
- kicker: `テキスト進行`
- title: `コード進行を入力`
- one concise common description

Do not show a separate large `拡張テキスト進行` page identity.
Do not create a tall 80px+ explanatory block.

Mode-specific notation help belongs in a compact legend/help row near the editor.

Standard helper preserves its actual rules/limits.
Extended helper explains `|`, `%`, `_`, `=` and its timing rules.

---

## 5. Shared Editor / Preview workspace

Both modes use the P8.8.2-style workspace:
- editor ~40%;
- preview ~60%;
- independent scroll surfaces;
- <900px Input/Preview tabs;
- no page-level horizontal overflow.

Standard must stop rendering one giant card for every chord.

---

## 6. Standard preview adapter

Map Standard parser output into the same preview primitives.

Standard semantics remain unchanged:
- one chord/bar -> full-bar band;
- two chords/bar -> current Standard timing contract;
- four chords/bar -> current Standard timing contract.

Do not invent Extended timing semantics inside Standard.

If input exceeds Standard capability:
- show clear Standard-specific diagnostic;
- when appropriate provide an explicit non-destructive `拡張で読む` action;
- never auto-switch modes.

---

## 7. Written spelling

Standard follows the same presentation rule as Extended:
- display user-authored chord spelling;
- internal canonical identity may remain canonical/enharmonic;
- `Db7(#9)` should display as `Db7(#9)`, not `C#7(#9)` solely because of internals;
- `BbM7` should display as `BbM7`, not be silently rewritten to `Bbmaj7`.

If Standard currently discards written labels too early, preserve them in view-model/presentation data without changing semantic identity or Vault fileVersion.

Add regression tests.

---

## 8. Key control

Use a common Text Capture key control where technically valid.

- candidate keys may be shown;
- explicit user confirmation remains required;
- never auto-confirm key;
- Standard/Extended share visual treatment;
- if a mode cannot infer candidates safely, allow manual/unconfirmed state rather than fabricating inference.

Key-dependent feature availability is summarized compactly near save/status.

---

## 9. Shared BPM control

Reuse the shared BPM scrub from P8.8.2/Voicing Loop.

Display:
`BPM  − [120] ＋`

Numeric area is the full vertical scrub target.
Preserve direct edit, vertical drag, wheel, keyboard, Shift/Ctrl modifiers, 30–240 clamp and Space suppression while editing.

P8.8.4 adds the live playback behavior in section 22.

Current Standard has large availability cards for Vault / Chord Dojo / Bass Practice / Chord Context / Root Motion / voicing-memory-like features.

Replace the large grid with a compact summary near save/status, e.g.:
`キー未確定のため Bass Practice / Chord Context / Root Motion は保存後にキーを設定すると利用できます。`

Allow an optional detail expansion.
Do not delete capability logic.

Do not delete these paths in P8.8.4.
Instead:

- keep Capture focused on Paste -> Inspect -> Hear -> Save.

A full move/redesign belongs to Phase 8.9.

Primary user flow should align toward Vault save where existing product contracts safely allow it.

If Draft conversion is still required internally:

Do not delete Draft editor support.

Preserve the P8.8.2 bottom/sticky save/status concept.

- `エラー2件を直すと保存できます`;
- persistence failure reason;
- practice limitation;
- key-dependent availability summary.

Footer should carry, as applicable:
- name;
- bar count;
- annotation count;
- meter;
- BPM;
- error/warning/practice counts;
- compact capability summary;
- save action;
- save-disabled reason.

---

## 14. Transport reuse

Do not invent a second unrelated scheduler.
Reuse/refactor Text Capture and Voicing Loop transport primitives where practical.

Protect:
- scheduler epoch/look-ahead guarantees;
- no double notes;
- no missing notes;
- no AudioContext recreation;
- P8.8.3 audition resolver.

Visual playback rendering must be decoupled from note-event firing cadence.

---

## 15. Smooth playhead

Problem: current vertical line visibly jumps.

Required:
- derive visual position from musical transport time;
- update via `requestAnimationFrame`;
- interpolate continuously inside current bar/span;
- do not rerender the whole long preview every frame;
- update only current/previous state + playhead position.

It must honor:
- actual meter;
- exact source ticks/timing;
- variable span durations;
- reattacks/holds/rests.

Never assume every bar is 4 beats.

---

## 16. Current playback indicator

During playback show:
- current bar;
- current HarmonicSpan/chord band;
- smooth playhead.

Use restrained emphasis:
- active bar frame;
- active band emphasis;
- optional short attack pulse.

Accessibility:
- transport state uses suitable `aria-live`;
- do not announce every animation frame;
- announce Play/Pause/Resume/Stop and seek target changes.

---

## 17. Exact chord/HarmonicSpan seek

Band click is NOT bar-level seek.

Stopped:
- seek to exact HarmonicSpan / selected attack start;
- audition that chord;
- remain stopped;
- next Play starts there.

Playing:
- seek to exact span/attack start;
- continue playback from there.

Paused:
- seek to exact span/attack start;
- audition it;
- remain paused;
- Resume continues there.

Also select/highlight the exact parser source span, not the entire line.

---

## 18. Bar-number seek

Bar-number click is a separate target.

Stopped: seek bar start.
Playing: seek bar start and continue.
Paused: seek bar start and remain paused.

Do not audition an arbitrary chord merely because bar number was clicked.

---

## 19. Play / Pause / Resume

Primary transport control states:
- stopped -> `▶ 再生`
- playing -> `Ⅱ 一時停止`
- paused -> `▶ 再開`

Behavior:
- stopped: play from current seek position;
- playing: pause at exact current musical position;
- paused: resume from it.

Space = same behavior, except while focus is in textarea/input/contenteditable/BPM direct edit or another editing field.

---

## 20. Play anchor and Stop

When Play begins, capture `playAnchor = current musical position`.

Stop:
- playing -> stop audio and return position to `playAnchor`;
- paused -> stop and return to `playAnchor`;
- already stopped -> no-op.

Do NOT use hidden double-Stop behavior.

Add an explicit `|◀` / `最初から` control:
- stopped -> seek beginning;
- playing -> seek beginning and continue;
- paused -> seek beginning and remain paused.

---

## 21. Loop scope

P8.8.4 Loop = whole current progression/playback snapshot.

Do NOT infer sections from arbitrary `#` annotations.
Do NOT add `このセクションを再生` unless a real Section model exists independently of comments.

---

## 22. Live BPM while playing

Decision:

Stopped:
- value changes; next Play uses it.

Playing:
- preserve current musical position;
- apply new BPM immediately;
- future scheduled events use new tempo.

Paused:
- value changes immediately;
- Resume uses new BPM from paused position.

Requirements:
- no restart to beginning;
- no musical-position jump;
- no duplicate already-fired notes;
- cancel/replace only future look-ahead events as needed;
- use epoch/reschedule mechanics;
- no AudioContext recreation.

Stress-test repeated BPM scrubs while playing.

---

## 23. Playback snapshot and live editing

Preserve P8.8.2 snapshot contract.

When Play starts, freeze playable note/timing snapshot.
During active playback:
- editor/preview may update visually;
- active audio remains on frozen snapshot;
- show `編集中の変更は次回再生から反映されます`.

Seek during an active snapshot must target the snapshot's stable span/attack IDs where possible.
Do not hot-swap newly parsed events into the current audio schedule.

If edits remove/restructure a target so mapping is impossible, keep audio snapshot valid and defer new structure to next Play. Never mix snapshots silently.
