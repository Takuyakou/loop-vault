## Product path and gaps

`TextProgressionCapturePanel` calls `parseTextProgression` and requires a
  conversion to `ManualCandidateDraft`. `CaptureView` builds a save payload;
  `vaultStore` normalizes it and writes a `SavedProgressionBlock`. The existing
  path saves canonical chords and score bounds but loses exact pasted text,
  source spans, section/comment data, and the distinction between harmonic
  spans and attack events. The `%` control currently creates another event.
  `=` extends the current event and `_` creates a gap.

The shared chord parser is `parseChordLabel` in `src/domain/chords.ts`.
Standard and extended modes can share that semantic core and the existing
memoized bar segmentation, with separate document/timing adapters. Product
MIDI extraction and Phase 9 candidates are outside this change.

## Vault v2 decision

`savedProgressionBlockSchema` is strict and currently has no text-source field.
An explicit, optional, bounded `textSource` member on a progression block can
be added to the v2 reader and writer without changing `fileVersion` or
overloading title, memo, source-MIDI fields, or descriptions. Old records omit
it. The store passes complete blocks through its mutation path; the repository
preserves quarantined raw records separately. Stage 04 must prove the new
member survives save → parse → unrelated edit → save → reload, and old Vault
records remain semantically unchanged. No migration of existing records is
planned. This is a backward-compatible v2 field addition, not a version bump.

## Timing and playback

The current text path is 4/4 with 1, 2, or 4 exact slots per bar. The PRE
contract confirms the same bounded grid for extended input; unsupported
rhythms stay diagnostic. The Vault Voicing Loop handoff builds detached
generated practice snapshots from stored chord events. Phase 8.8 will carry
text attacks in the optional text-source block and project them to timed
practice rearticulations without labeling text as SOURCE MIDI.

## Historical contract conflict

Older P5.20 wording names arbitrary repeat grammar unsupported, while current
product code accepts `%` as a repeat control. Phase 8.8 follows the current
implementation and the PRE contract: `%` means rearticulation of the preceding
harmony. A compatibility erratum will distinguish this from unsupported
repeat macros.
