## 3. 戻した音を修正作業場で編集・削除・役割変更したら何が起きるか

**コード名が作り直されるのは、「使う」にしたときだけで、それは修正作業場の中の計算（再解析ではなく表示側の名前付け）です。**

- 事実（`correctionModel.ts`・`edits.ts`）：音の編集（使う・外す・足す・高さを動かす）の後は `refreshModel(…, updateNames: true)` が呼ばれ、**自動の名前は「使っている音」から `detectedName` で付け直される**。人が打った名前は変わらない（提案だけ出る）。解析はやり直されない。
- 試した結果：戻したメロディの音を 2 小節目のカードで「使う」にすると、**Am7 → Am11（自動）**。ほかのカードは変わらない。つまり、**使うと拡張音として名前に入る**（解析のときと同じ判断。意図した動作）。
- 削除（外す）：戻した音は最初から「使わない」なので、変化なし（`changed: false`）。
- **役割変更**：修正作業場には、パートの役割を変える操作は**ありません**（`roleHint` は表示用の導出値のみ）。
- 修正作業場の「メロディの線」（線より上の使っている音を外す道具）：使っている音にだけ働くので、戻した音では何も起きない（`aboveLineIds` は空）。

つまり、**戻した音は「見える・選べる・使えば名前が変わる」。使わなければ何も変えない。**

## 5. 注意（実装するなら）

1. **効くのは「音域が離れた曲」だけ。** 重なる曲は線が出ない。画面にもそう書く（設計どおり「音域が重なる曲では分けきれない簡易的な方法です」）。
2. **メロディの音は解析の結果から消える。** 結果の見出しの「（線で分けたパートあり）」は、その意味で意味がある（承認済み）。保存の `sourceFingerprint` は解析に渡した音から計算されるので、同じファイルでも、線の有無で変わる。
3. **「アプリに任せる」について**：この合成データでは、和声コアは「分けない」と同じ結果でした（25% → 25%、50% → 50%）。**画面の説明「メロディ由来の誤検出を減らします」は、旧画面の文言**で、新しい画面では「解析のときに、音の動きからアプリが見分けます。和音の名前を決め直すときは、ベースを見ません」としています。後半は事実ですが、前半の「見分けます」も、この合成データでは名前に効果が出ていません。**直していません（別に控えるとのことでした）**。
4. 解析に渡す音を減らすので、「何も変えずに解析」の経路（元のバイト列）には流れない（線のあるセッションは、設計どおり準備した経路を使う）。
