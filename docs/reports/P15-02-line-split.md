統合テスト（`splitIntegration.test.ts`、合成データ・実際のストア・保存と読み直し）：
- 線を引く → 解析 → 修正作業場に戻した音が「使わない」で出る（解析に渡った音には線より上が無い）。

## 5. 実曲での確認（受け入れの条件）：手順

MIDI が届いたら、同じ手順で表にします（合成データでは、メロディは「コードの音ではない音」か「半々」の作り物です）：

```
P15_REAL_MIDI=<.mid のファイルまたはフォルダ> npx vitest run src/domain/preAnalysisParts/realMidiCompare.test.ts
```

（線を指定するときは `P15_LINE=<MIDI のノート番号>`）。小節ごとの名前を 4 方式（分けない / アプリに任せる / 線で分ける / 線＋アプリに任せる）で並べ、違う小節に印をつけます。実曲に正解表はないので、**表を人が読んで判断**します（ファイル名とパートの情報だけを出力。MIDI の中身は出しません）。
合成データで通ることの確認として、手順を `synthetic.mid` で試しました（4 小節が変わり、Am11 → Am7 などになる）。

## 6. 注意・限界

- **効くのは音域が離れた曲だけ**です。重なる曲は線が出ません（画面にも書いてあります）。
- **線より上の音は、コード名の判定から完全に外れます**（`melody-weak` の「弱く効く」ではない）。メロディにコードの音が含まれていても、同じです。その音を名前に入れたいときは、修正作業場で「使う」にします（名前が変わる）。
- 修正作業場の元データは、解析時に確定します。**線を解析の後で動かしても、結果の画面は変わりません**（「変更する」から戻って解析し直す）。
- 実装中に見つけて直した不具合：修正作業場は、結果が出た時点のモデルを 1 度だけ取り込むため、解析の完了後に「戻す情報」をセットしても反映されなかった（e2e で発見）。解析を始める前にセットするようにした。

## 7. Stage 03 の判断材料

「前回と同じ設定」に線の高さを含めるなら、線は**セッションの外では意味を持たない値**（パートの id に結びつく）です。保存するのは「パートの並びの特徴」ごとの `melodyFrom` の音名だけにして、ファイル名・トラック名は含めない形になります。適用は押したときだけ（決定済み）。
