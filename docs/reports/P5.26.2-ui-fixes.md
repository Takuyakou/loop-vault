## 3. Stage 01：進行モードの「曲全体」

**原因**：`ProgressionWorkspacePage.tsx` が、進行の版を選ぶボタンの列を「曲全体」として差し込んでいました（`CorrectionWorkspace` の `progression.overview`）。

**直したこと**
- 進行モードでも、取り込み側と同じ帯（`CorrectionWorkspace.tsx` の `lv-cw-overview-row`）を出す。差し込みの口（`ProgressionWorkspaceOptions.overview`）と、ボタン列の CSS を削除。
- 帯の機能は作り直していません（枠・再生ヘッド・クリック／ドラッグ移動は元からありました）。再生ヘッドは rAF + `transform` のままです。

**ヘッダーのセレクトがボタン列を包含しているか**：包含しています。
- どちらも同じ `ordered` の一覧で、同じ `openProgression`（未保存の変更があれば確認を挟む `guard` 経由）を呼びます。
- セレクトは名前に「・別の版」の印も付き、`この曲の進行（n）` で個数も出ます。
- ボタン列にあってセレクトに無いのは「全部の名前が一目で見える」ことだけです。ヘッダー側には足していません。

**要確認の位置と「次の要確認」**：保存した進行のカードには要確認の印がありません（P10.4 で「保存したカードは確定したもの」とし、`reviewReasons` は常に空。既存の E2E `correction-workspace-save.spec.ts` もそれを確かめています）。そのため、進行モードの帯には要確認の点が出ず、次の要確認の操作も出ません。取り込み側の「次の要確認」（`]` `[`、ボタン、末尾から先頭へ回る）は変えていません。これは仕様どおりで、「進行モードで次の要確認が動く」ことは確かめようがないため、「点が出ない・ボタンが出ない・`]` を押しても何も起きない」ことを確かめました。

**DOM 要素数（300 小節の曲を取り込んだ時の帯）**：計 377 個（カード 300・区切り 38 とその名前 38・枠 1 ほか）。128 小節なら約 160 個の見込みです。数百のオーダーなので、間引きは入れていません。

**テスト**（`e2e/p5-26-2-overview.spec.ts` 6 件）：帯が出て版ボタンではない／枠が本体のスクロールに追従／帯クリックで本体が移動・ドラッグで動き続ける／再生中に再生ヘッドが動きカードが作り直されない・手動スクロールで追従が切れる／版の切り替えができる・要確認が出ない／取り込み画面の帯は変わらない。
パッケージのテスト 5（再生中にコードカード列が再描画されない）は、E2E では描画回数を数えられないため、「カード列の DOM が作り直されない（`childList` の変化が 0）」で確かめています。

## 4. Stage 02：Voicing Loop の指スロット

**度数 `—` の原因**（想定と一致）：`noteFacts`（`voicingResolution.ts`）が、コードの構成音と足した色の度数にしか度数を付けず、それ以外の音は `null` にしていました。画面（`formatChordToneList`）が `null` を `—` と出していました。B♭9 の F♯5 がその例です。
**直し方**：領域側（`null` の意味は「構成音の外の音」）は変えず、表示で「コードのルートからの音程」を常に出します（`1 ♭9 9 ♯9 3 11 ♯11 5 ♭13 13 ♭7 7`）。`—` はルートが分からない時だけ。構成音でない音は、斜体・薄い色にして区別します。

**パネル幅の原因**：「次」のパネルが、両手に音がある時 `0.35fr : 0.65fr` の可変幅で、片手が空だとその手のパネル自体が消えていました。「今」のパネルも、使う指だけを詰めて並べていました。
**直したこと**：左右とも常に 5 スロット（`L5 L4 L3 L2 L1 | R1 R2 R3 R4 R5`、画面の並びが鍵盤の並び）の表（`table-fixed`）にし、左右を同じ幅の 2 列にしました。使わない指は `·` の空きスロットです。片手が 5 音を超える時は、スロットを増やさず下の補助行に出します。
**新しい部品**：`src/voicingPractice/handSlots.ts`（並べ方と度数。純関数）、`src/components/voicing/HandSlotPanel.tsx`（表）。

**直した今のテスト（理由つき）**：旧い「詰めた文字列」を見ていた所を、スロットの位置で確かめる形に直しました。見ている事実は同じです。
| ファイル | 直した所 | 理由 |
| --- | --- | --- |
| `ProgressionVoicingPracticeView.test.tsx` | `構成音1 · 3 · 5`、`指R1 · R5`、`R2 · R5自分の運指`、`R1 · R5おすすめ`、`L5 · L1` など 7 件 | 詰めた表記が無くなった（使っている指の位置・各スロットの内容で確かめる） |
| 同 | 「片手が空なら手のカードが無い」 | 空の手も 5 つの空きスロットのパネルになった |
| `e2e/phase5.27-voicing-loop-ui.spec.ts` | `G4 · B4`、`5 · 7` ほか | 同上 |
| `e2e/phase11-source-selector.spec.ts` | 片手だけの固定で、左のパネルの数が 0 | 左のパネルは出て、使用中のスロットが 0 |
| `scripts/p11-12/uiAudit.test.tsx`・`FingeringRankerAcceptance.test.tsx` | `L5 · L1` など詰めた指の表記の `toContain` 5 件 | 使っている指のスロットを見る形に（FULL で見つかった） |

**テスト**：`handSlots.test.ts` 8 件（常に 5 スロット、B♭9 の右手で R4 が空き、並びが音高の昇順、6 音目のあふれ、12 のルート × 12 の音程すべてに度数が付く、ルート不明の時だけ `—`）、`e2e/p5-26-2-voicing-slots.spec.ts` 3 件（コードを切り替えても、左右のパネルの幅と各指の位置が同じ。使わない指が空き。度数に `—` が無い）。

2. **内容**：色（緑 `#5fd39a`）と ✓。カードにはアニメーションも音も付いていません。持続は「その回の間」。
3. **同一コンポーネントか**：**別実装**でした。Master のカード、Chord Dojo の進行のカード（`ChordDojoView.tsx`）、1 コードのカード（`.dojo-prompt-card`）、ランダムキーのカード（`ChordDojoEndlessView.tsx`）は、それぞれ別の JSX でした。
4. **`practice` の項目**：`confirmedLevel` / `provisionalLevel` / `clearedKeys` / `lastPracticedAt` は Chord Dojo の記録には**ありません**（別の機能（`src/domain/practice/`）の項目です）。Chord Dojo の記録は、項目ごとの `state`（provisional / passed …）とキーごとの記録（`lastAt`・`bestSec`・`self`）で、自己申告と鍵盤の別はすでに `self` で分かれています。

### 5.2 入れたもの
- 共有の印 `src/components/practice/ChordCardResult.tsx`（`ChordCardResult { state, source }`、`ChordCardMark`、`useCardMoment`）と CSS。Master・進行のカード・1 コードのカード・ランダムキーのカードが、この印を使います。
- **瞬間（400ms）**：カードの枠が光り、左上に印が出て、**自動で消えます**（`CARD_MOMENT_MS`。外れた時は ✗ を同じ長さで）。
- **この回**：弾けたカードの印が残ります（進行のカードは小さい欄の中、1 コードのカードとランダムキーのカードは左上）。キーが変わると消えます。
- **鍵盤と自己申告の別**：鍵盤 = 塗りの円の ✓、自己申告（「弾けた」）= 中空の輪の ✓、外れ = 輪の ✗。色だけではなく形で分けています。
- 度数の常時表示・カードを押して鳴らす動きは変えていません（既存の E2E が通ります）。
- 印の位置は左上です（右上は P12.3 のスピーカーのボタンの場所）。

### 5.3 入れていないもの（判断をお願いしたい所）
1. **正解の音（瞬間の層の「音を 1 つ鳴らす」）**：入れていません。理由：鍵盤を弾くと「入力音」がすでに鳴っているため、重ねて鳴らすと自分の音と混ざる可能性があること、音を出す／出さないの設定が新しく要ること（今の保存の形では置き場が無く、per-viewer の設定になる）です。入れる場合は、`playbackController` で短い 1 音を鳴らし、設定に「正解の音」を足す形を考えています。
2. **累積の層（カード下端のドット列）**：入れていません。理由：Chord Dojo の記録は「カードごと」ではなく「キーごと」で、キーごとの塗り／中空（自己申告）は 12 キーの表（`DojoKeyGrid`）がすでに出しているため、カードの下に同じものを足すと高さが増え（1280×720 で収める今の配置を崩す）、二重になります。カードの下に置くなら、そのキーの中での進捗にしかなりません。
3. **判定基準の表（指示書 §4）と、今の判定の違い**（変えていません。数値は仕様どおりではありません）：

   | 項目 | 指示書の表 | 今の実装（`judging.ts`） |
   | --- | --- | --- |
   | 型を覚える | ピッチクラスの一致（転回・オクターブ・重複を許す） | 「型」（`shape`）は、一番下の音・上の声部の並び・形の広がりも見る。ピッチクラスだけなのは「構成」（`composition`）の練習 |
   | 登録した音を覚える | 実音（オクターブ込み）の一致 | 同じ（`exact`）。ずれた時は「音域が違います」 |
   | 余計な音 | 不正解 | 同じ。ただし、全部の音が揃う前に離した音は数えない |
   | 揃えるまでの猶予 | 250ms | 必要な数の音が揃った最後の音を押してから `settleMs`（既定 **60ms**、設定は 0〜1000ms） |
   | 自己申告 | `confirmedLevel` に昇格させない | 記録に `self` で残り、合格などの数え方で分かれている（既存の仕組み） |

   この表の「今の実装」の列を、`src/domain/chordDojo/judgeCriteria.test.ts`（12 件）で固定しました。**指示書の表に合わせて判定を変える**なら、記録の意味と既存のテストが変わるので、別の作業として決めてください（250ms にするだけなら設定値の既定の変更で足ります）。
