# VL-14: Voicing Loop の一時停止 → 再開のカクつき(修正・検証・停止)

対象: `fix/vl-14-resume-stutter`(master `5dde13f2` から)。**master へのマージ・push はしていない。**

指示のとおり、`ProgressionVoicingTransport` を**承認された形**で変更し、直す前と直した後の数字をそろえて停止する。

---

## 0. 結論(先に)

- **原因**(調査で確定): 再開後、最初の `onTransportBeat` が **85〜100ms 遅れて**届く(Tone の先読み lookAhead 既定 0.1秒 と一致)。表示は止めた拍 + 1/16拍 で止まり、最初の知らせで **0.12〜0.19拍 飛ぶ**。
- **見立ては数字で確認済み**: 最初の sync は再開から壁時間で +94.9〜129ms、最初の音は音時計で +100〜111.6ms 後。いずれも lookAhead 0.1秒。→ 再開の瞬間に拍だけ送っても、音が +0.1秒 に鳴る間、表示は 1/16 上限で止まって飛ぶ、という見立てどおりだった。
- **修正**: 承認された形 — transport が「(拍, その拍が鳴る音の時刻)」を開始・再開・シーク・区間切り替え・再スタートで**すぐに 1 回**送り、画面は**最後に受けた組と音の時計**から位置を出す。時刻が未来の間はその拍で止め、鳴り始めたら滑らかに進める。
- **結果**: 全シナリオで**飛びは消えた**(最大 0.026拍、しきい値 0.06 未満。直す前は最大 0.19)。表示と音のずれは最大 **0.088拍**(§3 の 1/8 = 0.125 以内)。残るのは再開・シーク直後 **約 86〜101ms の「音が鳴るまでの待ち」**(指示 3 が明示的に認める挙動。音もまだ鳴っていない)。
- カウントイン無しの開始・再生中のシークも測った。どちらも飛びなし。開始では**最初の sync の時刻と最初の音の予定時刻が一致**(0.208 = 0.208、0.220 = 0.220)。
- `clock.ts` は**未変更**(`RESUME` / `SYNC_TRANSPORT` の決まりはそのまま)。

## 1. 承認された方針と実装の対応

| 指示 | 実装 |
|---|---|
| 1. `onTransportBeat` に「拍」と「その拍が鳴る音の時刻」を送る | `onTransportBeat(absoluteBeat, audioTime)` に 2 引数化。拍だけを受け取る Chord Dojo テンポ練習(`ChordDojoView.tsx` は `beat => ...` の単引数)はそのまま動き、e2e(p12 テンポ練習一式)で確認 |
| 2. 開始・再開・シーク・区間切り替えで「音開始時刻 + その時の拍」をすぐ 1 回送る | `start`(v1/v2 の両分岐)/ `resumeOnce` / `seek`(カウント内は `remainPaused ? Tone.now() : Tone.now() + 0.05`、通常は `Tone.now()`)/ `setLoopBounds` の `apply`(第 2 引数 `time`)/ `restartOnce` で即時送信 |
| 3. 画面は最後に受けた(拍, 時刻)と音の時計から描く。未来の間はその拍で止める。`performance.now` は使わない。1/16 上限は途絶時の安全だけに残す | `latestTransportRef` に常に組を保持(一時停止中も)。`paint` は `soundBeat()` = `pair.beat + min(cap, max(0, nowAudio − (pair.time − outputLatency)) / spb)`。`nowAudio` は `getOutputTimestamp().contextTime` を優先(なければ `currentTime`)、出力遅れ `outputLatency` 込み。上限は **0.25拍**(根拠は §6) |
| 4. `clock.ts` を変えずに済むならそのまま | **未変更**。`RESUME` / `SYNC_TRANSPORT` の減速規則に触れていない |

`visualTransportBeat`(壁時計で補間する旧関数)は画面から**使用をやめた**(関数と単体テスト自体は存置)。`performance.now` は記録用と ページめくりアニメーションなど従来の用途のみで、再生位置の計算には使っていない。

## 2. 見立ての検証(直す前に数字で確認)

直す前の実装で、再開 → 最初の知らせ/最初の音を測った(修正前コミット `a8b5d9ff` + 計測用 probe):

- `lookAhead` = **0.1秒**(全 sync で一定)
- 再開 → 最初の `onTransportBeat`:壁時間で **+94.9〜129ms**
- 再開 → 最初の音(スケジュール時刻):音時計で **+100〜111.6ms**
- 再開直後の表示:止めた拍 + 1/16拍 で停止(例: 9.0 → 9.0625 で停止 → 9.185 へ飛ぶ)

→ **遅れ ≒ lookAhead(0.1秒)で確定。** 音が鳴り始める前(~0.1秒)に表示だけ進める手段は旧実装になく、1/16 上限のせいで「止まってから飛ぶ」になるとおりだった。

- 記録内容: `frames`(描いた拍・absoluteBeat・audioNow)、`syncs`(届いた拍と音の時刻・`lookAhead`・`contextTime`・`outputLatency`・破棄)、`marks`(開始/一時停止/再開/シークの印)、`effectStarts`。

  - 再開系の最大飛び ≤ 最初の開始 + 0.03拍(§3「同じくらい」)

複数回の実行範囲: 飛び 0.016〜0.028、ずれ ≤ 0.088、hold 47〜94ms、最初の sync 前 117〜608ms(ページ起動後最初の開始は AudioContext 起動を含む)、即時 sync 1.5〜8.6ms。

読み方:

- **再開の「止まり」は消えていないが、性質が変わった。** 直す前は「音が鳴っているのに表示だけ止まり、その後 0.12〜0.19拍 飛ぶ」だった。直した後は **pair の時刻(=音が鳴る時刻)が来るまで ~90ms 停止し、音が鳴った瞬間から滑らかに動く**(飛びは 0.02〜0.03拍 = 定常の描画と同水準)。これは指示 3 の「時刻が未来の間はその拍で止めておき、鳴り始めたら滑らかに進める」どおりで、停止中は**音もまだ鳴っていない**。
- 再開直後の最初の sync は壁時間 **+1.5〜2.5ms**(直す前は +94.9〜129ms)。シークは **+7.8〜8.6ms**。
- **カウントイン無しの開始**(クリック直後〜): 飛び 0.022〜0.023、後退 0。ページ起動後最初の開始では音を待つ停止 **608ms**(AudioContext 起動 ~400ms を含む)、2 回目以降は **~116ms**。どちらも音の予定時刻までの待ちで、音が鳴り始めると滑らかに動く。
- **カウントインありの開始**: 停止 190ms(同様に起動を含む)、飛び 0.0247、後退 0。
- **最初の sync の時刻 = 最初の音の予定時刻**(カウントイン無し開始 0.208 = 0.208、カウントイン開始 0.220 = 0.220、差 0.0ms)。transport が送る「音開始時刻」が実際の音と一致している。
- **再生中のシーク**: 飛び 0.017〜0.024、後退はシークの再アンカーとして正当なもののみ。直す前の「~67ms 止まり+小さな飛び」に対し、飛びが消えた(hold は同じく音が鳴るまでの待ち)。
- **表示と音のずれ**は全区間 ≤ 0.088拍(§3 の 1/8 = 0.125 以内)。「再開系の飛び ≤ 最初の開始 + 0.03拍」も全窓で満たす(0.021〜0.026 vs 0.025)。
- **停止**すると再生ヘッドは旧実装どおり **0 に戻る**(VL-07 契約)。初回の `npm run test:full` で、pair を保持し続けたために停止後も最後の位置を描く退行(VL-07 `voicing-loop-v2` 1件)を検出 → 修正(§7)した。

## 6. 上限 0.25拍 の根拠

- 定常時の補間に必要な量: sync は約 33〜38ms ごと(BPM100)= **0.055〜0.064拍**。実測の定常ずれの最大は **0.088拍**。
- したがって **0.25拍 は通常動作では一度も使われない**(全窓・全実行で cap 到達なし)。sync が途絶えたときだけ効く安全上限で、途絶時の表示は最大 0.25拍 まで進んで止まる。
- 旧上限 1/16(0.0625拍)は、sync 間隔ひとつ分(0.055〜0.064拍)と同量だったため、止まっている間に 1/16 だけ進んで止まる、という見た目を作っていた。
